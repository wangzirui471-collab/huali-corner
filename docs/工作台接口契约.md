## 1. 这份文档现在的用途

第一版写它的时候，工作台前端做完但后端三个接口归属另一批改动，
所以先按契约冻结了接口形状，前端带上兜底提示。

**三个接口现在都已实现**，兜底提示不会再出现。契约留在这里，
是因为它记录了「每条权限背后必须做哪几件事」——这些约束比接口签名更重要，
后续改动不要漏掉：

- 强制下架必须**同时**写审计、通知卖家、并切断卖家自行恢复的路径（三件事缺一不可）
- 商品复核必须能把 `moderation.reviewed` 置回 `true`，否则中危商品永久停在「审核中」
- 查阅档案必须留痕，且手机号脱敏

`actions/staff.js` 顶部的 `PENDING` 兜底分支现在已经是死代码，
下次改这个文件时可以顺手删掉。

## 2. 三个待接接口

### 2.1 `POST /api/product/moderate` —— 平台强制下架 / 恢复 ✅ 已实现

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `id` | int | 是 | 商品编号 |
| `action` | string | 是 | `delist` 下架 / `restore` 恢复上架 |
| `reason` | string | 是 | 处置理由，≤500 字。**会写入审计并展示给卖家** |

**服务端必须做的四件事**（缺一件这条权限就不成立）：

1. **写审计**：`audit(actor=操作人, target=卖家, type='product_moderate', reason=理由)`
2. **通知卖家**：写一条站内通知（复用缺陷修复里新增的 `notify()`），
   内容包含商品编号、处置理由、申诉入口
3. **切断卖家自行恢复的路径**：被平台下架的商品，卖家调
   `set_product_status(action='relist')` 必须被拒。现在只有 `removed_by` 这一层能区分
   「卖家自己下架」和「平台下架」，建议给 `products` 加一列
   `delisted_by INTEGER DEFAULT 0`（0=卖家自助，>0=平台处置人 id），
   在 `set_product_status` 里加一句 `require(delisted_by==0, '该商品由平台处置，请在客服中心申诉')`。
4. **利益冲突**：操作人不能是商品卖家（`require(p['seller_id'] != u)`），
   复用 `SupportService.check_conflict` 的既有口径。

建议放在 `CatalogService`（它已经持有商品写路径），
参考既有的 `set_product_status` 写法，别新开一套。

> ⚠️ 第 3 条是这条功能的关键。没有它，管理员下架后卖家点一下「重新上架」就绕过去了，
> 等于白做。这一条**必须在同一次改动里一起提交**。

### 2.2 `POST /api/product/review` —— 中危商品的人工复核 ✅ 已实现

自动审核把「平台限制」类目的商品标成 `under_review`（写在 `products.data.moderation`），
但**现在没有任何代码把 `moderation.reviewed` 改回 `true`**，
所以中危商品会永久停在「审核中」角标上，`message_for()` 承诺的
「通过后会正常展示」无法兑现。这个接口就是那个缺口。

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `id` | int | 是 | 商品编号 |
| `decision` | string | 是 | `approve` 通过 / `reject` 驳回并下架 |
| `reason` | string | 否 | `reject` 时必填 |

**行为**：

- `approve`：把 `data.moderation.reviewed` 置 `true`（商品 `under_review` 随即变 `false`），
  给卖家发通知；商品保持 `available`。
- `reject`：按 2.1 的同样要求下架（含 `delisted_by`、审计、通知）。
  实现上可以直接复用 2.1 的 `moderate_product`。

**建议放在 `CatalogService`**，与 `moderate_product` 相邻。

### 2.3 `GET /api/user/dossier?id=` —— 用户档案 ✅ 已实现

档案页第一版是**用既有接口拼出来的**（`/api/profile` + `/api/admin` + `/api/tickets`
三个并行请求再在前端过滤）。现已换成一次调用，原因不只是省请求：

| 数据 | 第一版来源 | 现在来源 |
|---|---|---|
| 公开资料 | `/api/profile?id=` | `/api/user/dossier?id=` |
| 角色 / 状态 / 信誉分 | `/api/admin` 用户表（要拉全站用户） | 同上接口 |
| 信誉变动与处置留痕 | `/api/admin` 的 `audit` + 前端过滤 | 同上接口 |
| 该用户提交的工单 | `/api/tickets` 全部 + 前端过滤 | 同上接口 |
| **订单** | **拿不到**（`/api/orders` 只返回自己的） | 同上接口 |
| **查阅留痕** | **没有** | 每次调用写一条 `dossier_view` |

接口返回：

```
GET /api/user/dossier?id=42        （仅 staff）
{
  "user":   {id,nickname,college,major,education,bio,score,role,status},
  "phone":  "138****0001",          // 脱敏，不给完整号码
  "orders": [{id,buyer_id,seller_id,status,total,created,role}],  // 最多 50 条
  "products": [...],
  "tickets":  [...],
  "audit":    [...],                // 该用户被处置的记录，最多 100 条
  "served_by": 操作人id
}
```

**两条硬约束**：

1. **手机号必须脱敏**（`138****0001`）。工作台不需要完整号码就能干活；
   真需要联系时再走单独的高敏流程。
2. **查阅本身要留痕**：写一条 `audit(actor=查阅人, target=被查人, type='dossier_view')`。
   前端已经在 `AUDIT_LABELS` 里预留了 `dossier_view: '查阅用户档案'` 的显示名。

> 这三条落地后，档案页可以把「并行调三个接口 + 前端过滤」换成一次调用，
> 顺带修掉 `/api/admin` 一次返回全站用户表带来的浪费。

## 4. 已落地的测试

`tests/test_product_moderation.py` —— 26 项，分两组：

**平台处置（21 项）**

| # | 断言 |
|---|---|
| 1 | 普通用户调 `/api/product/moderate` 返回 403；**客服可以**（治理不该只压在管理员一人身上） |
| 2 | 操作人不能处置自己发布的商品 |
| 3 | **平台下架后，卖家 `set_product_status(relist)` 必须失败** ← 最容易被漏掉、也最要紧的一条 |
| 4 | 卖家自己下架的商品不受影响，仍可自行恢复 |
| 5 | 恢复上架会清掉 `delisted_by`，控制权还给卖家 |
| 6 | 已预留商品不能强制下架（挂在别人订单上，要走工单流程） |
| 7 | 下架会清掉未到期的置顶 |
| 8 | 下架写 `audit`，且卖家收到站内通知 |
| 9 | 理由必填 |
| 10 | `approve` 清掉 `under_review`；`reject` 走强制下架（含 `delisted_by` 与通知） |
| 11 | 没有待复核标记时不能复核；同一商品不能复核两次；`reject` 理由必填；非法结论被拒 |
| 12 | 商品不存在返回 404 |

**用户档案（5 项）**：普通用户 403；返回六个集合；手机号脱敏；查阅写 `dossier_view`；每次查阅单独计数。
