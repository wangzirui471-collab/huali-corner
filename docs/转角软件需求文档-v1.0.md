# 转角软件产品需求文档

**版本：V1.0 · 需求评审稿**

**更新日期：2026年10月15日（Asia/Shanghai）**

**产品名称：转角；英文图形标识方向：ZJ**

**适用范围：手机网页、电脑网页、微信小程序、客服与管理后台**

> 本文整理整个软件的产品需求，供产品设计、开发、测试和运营使用。功能要求不等于功能已全部实现，更不等于已经上线。现阶段采用模拟交易；正式支付、正式小程序发布和公网运营分别验收。

## 1. 产品定位与目标

转角是面向校园的二手交易与交流平台，帮助学生、毕业生出售闲置物品，让有需求的同学以较低成本购买，并通过平台订单、交付记录和售后渠道减少交易纠纷。

首批从广州华立学院广州校区的**计算机工程学院**试点，先覆盖少量专业、真实卖家和真实求购需求。商品以**逐本二手书、宿舍日用品、运动闲置**为主，暂不以高价数码或奢侈品为核心。

产品希望完成三个基本结果：

1. 卖家能方便、如实地发布物品，买家能看清版本、缺陷、价格和交付方式。
2. 双方能在平台内沟通、出价、下单、约定交付，并在发生问题时留有可核查的记录。
3. 校园社区帮助同学交流、发布求购和认识其他卖家，但社区热度不作为交易信用担保。

### 1.1 已确定的经营约束

| 项目 | 要求 |
| --- | --- |
| 运营者 | 个人试做，当前没有公司主体 |
| 试做预算 | 人民币3,000元；不得将该预算理解为已经购买服务 |
| 首期地域 | 广州校区，优先计算机工程学院试点 |
| 注册资格 | 不要求学生证明或实名认证，毕业生可以使用 |
| 首期登录 | 手机号＋密码；不发送短信，手机号归属暂未验证 |
| 交易 | 模拟支付、模拟退款、模拟结算，不收取真实货款 |
| 客服时间 | 每天08:00—20:00，中国标准时间 |
| 品牌 | 统一使用“转角”；旧名称“华立转角”需要逐步替换 |

### 1.2 试点成效

观察注册人数、真实有效商品数、求购响应、模拟下单完成率、取消原因、纠纷原因和客服处理时间。模拟成交量必须与未来真实成交量分开统计，不将测试数据当作平台业绩。

首轮建议邀请10—30名同学，完成至少5组买卖双方的完整试用，再决定是否扩大范围。这是试点建议，不是已完成的运营成果。

## 3. 用户角色与权限

| 角色 | 主要权限 | 限制 |
| --- | --- | --- |
| 游客 | 浏览公开商品、公开帖子和公开主页 | 发布、下单、聊天等写入操作需要登录 |
| 普通用户 | 同一账号可以买卖；发布、下单、沟通、参与社区、提交工单 | 只能查看和操作自己有权访问的数据 |
| 群管理员 | 处理所管理群的违规消息、禁言等 | 不具备退款、账务、全站信誉调整权限 |
| 群主 | 群管理员权限及群内管理职责 | 不能任意授予平台管理权限 |
| 客服 | 处理授权范围的反馈、售后、证据和协商记录 | 不处理自己的交易，不任意修改账务 |
| 平台管理员 | 角色授权、违规处置、申诉复核、运营设置与审计 | 敏感操作留痕，避免利益冲突 |

普通注册必须只获得普通用户权限。群主、群管理员可由成员推荐或申请，经平台审核后授予；用户不能通过修改网页请求获得管理权限。

## 4. 页面与导航

### 4.1 用户端

手机端建议采用五个主入口：**首页、社区、发布、消息、我的**。收藏放在“我的”和商品详情中，避免挤占主要导航。

| 页面 | 主要内容 |
| --- | --- |
| 首页 | 校区与试点提示、搜索、分类、商品卡片、筛选与排序 |
| 商品详情 | 实拍图片、介绍、价格、版本与缺陷、交付方式、卖家、互动和购买入口 |
| 发布/编辑 | 分类、图片、书籍或闲置字段、定价、送货费、地点和可交付时间 |
| 订单确认 | 单件或同卖家多件清单、交付方式、费用明细、地点和时间 |
| 订单详情 | 当前状态、待办、计时说明、交接记录、取消或售后入口 |
| 社区 | 求购与交流帖子、评论、总聊和分区群入口 |
| 消息 | 私聊、群聊、报价与订单通知、售后通知 |
| 个人主页 | 昵称、自愿公开的资料、在售商品及允许公开的动态 |
| 我的 | 我的发布、买入/卖出订单、收藏、信誉、客服、设置 |
| 客服中心 | 服务时间、工单提交、处理进度、回复、申诉 |

### 4.2 管理端

提供独立的客服与管理工作台，适合电脑操作，涵盖工单队列、内容举报、违规记录、信誉与申诉、群管理、目录维护、模拟账务与备份状态。

### 4.3 视觉要求

借鉴闲鱼、转转的搜索、分类、双列商品卡片和显著发布入口，形成转角自己的界面。商品图片与价格优先，不使用过大的宣传区挤占商品展示。

手机端不出现横向溢出；电脑端合理利用宽度。每个页面应有加载、空内容、错误、重试和无权限状态，不允许出错后永久停留在加载提示。

Logo需要让用户迅速理解“二手交易”。ZJ与转角元素可结合交换箭头、物品或价格标签，配合“校园二手交易”文字；仅抽象字母不能作为最终验收依据。最终配色和Logo方案尚未确定。

## 5. 账号、资料和隐私

### 5.1 注册与登录

1. 使用手机号和密码注册，昵称必填；展示手机号暂未验证的说明。
2. 不要求身份证、学生证、学号、学校邮箱或人脸材料。不将用户标为“实名”“本校认证”。
3. 手机号不可重复注册；密码不得明文存储。当前试用规则为12—128字符。
4. 支持登录、退出、修改密码和安全恢复；连续错误尝试应限速或暂时锁定。
5. 无短信验证时，账号恢复需恢复码或经运营者另行核实归属，不能仅输入手机号重置他人密码。
6. 改密或恢复后使旧会话失效。注册或登录失败应给出可理解的原因，避免无限转圈。

### 5.2 个人资料

可填写头像、昵称、学校、学院、专业、就读层次或毕业状态、个人介绍。学校及学院资料为自愿填写的资料，不是身份认证；未填写不阻止基本注册。

就读层次与毕业状态应分开表达，避免把“已毕业”当作一种学历。首期面向本科、专科及毕业用户；暂不建立中专市场和中专社区。

首期界面突出计算机工程学院试点，不能宣称已验证访问者的学院身份。后续学院扩展不应要求重新注册账号。

### 5.3 数据可见范围

| 数据 | 可见范围 |
| --- | --- |
| 商品标题、价格、商品图、公开介绍 | 可公开浏览 |
| 昵称、自愿公开的学院与专业、在售商品 | 公开主页可见 |
| 手机号、恢复信息、私人购买凭证 | 不出现在公开页面和公开接口 |
| 私聊 | 相关双方；投诉调查按授权和告知规则处理 |
| 订单交付详情 | 交易双方及有业务需要的授权人员 |
| 售后证据与内部处理记录 | 相关用户按权限查看，内部备注不公开 |

注册和上传时说明数据用途。对外试用应提供隐私说明、账号停用及删除申请渠道，并说明依法或为争议处理需要保留的记录。

## 6. 学校、学院、专业和楼栋目录

校区 → 学校/办学单位 → 学院/系部 → 专业，为可维护的目录关系。广州校区先开放，其他校区暂不开放。

现有上传表格只用来提取去重后的学院、专业和层次信息。不得导入学生姓名、学号、补考、成绩等个人记录；原表不得进入代码仓库或公开资源。

表格不能证明当前组织设置完整准确。同名、旧称、新称需核对后合并；**广州校区学校数量及当前正式学院目录尚待官方核实**，不能将表格中的多个学院名称算成多个学校。

楼栋选项来源于用户提供的地址截图，公开试点前需核实其所属校区与实际名称。优先使用公共碰面点，不要求填写宿舍房号。

## 7. 商品发布、二手书与浏览

### 7.1 通用发布字段

| 字段 | 要求 |
| --- | --- |
| 标题、分类、商品介绍 | 必填；介绍由卖家提供 |
| 售价 | 必填，非负数；后台按整数分处理；允许免费转让 |
| 购买时间 | 填日期、年月或明确选择“不记得/未知” |
| 成色、功能与缺陷 | 必填选择并可补充说明，不允许隐瞒已知问题 |
| 商品照片 | 发布至少3张不同实拍图，最多9张，可指定封面 |
| 交付方式 | 自提、校内送货、两者皆可；至少一种 |
| 送货费 | 支持送货时填写，免费送货显示0元 |
| 自提点、交付范围和时间 | 按交付方式填写，使用公共地点 |
| 来源或购买凭证 | 可选；凭证不公开，不算入3张必需商品图 |

至少3张图分别覆盖正面、侧面和顶部。书籍对应封面、书脊侧面和顶部书页。相同文件不能重复凑数；必要时可要求补拍缺陷或带指定文字的同框照片。

图片数量、文件重复检查和拍摄提示均不能保证排除网图。平台不得宣称仅凭图片已鉴真。上传应校验格式与大小、去除位置等元数据，禁止公开包含证件或他人隐私的照片。

商品支持草稿、在售、交易锁定、已售、下架及违规限制等状态。可编辑在售商品；已生成订单保存原信息快照，不能被后续编辑悄悄改变。

### 7.2 二手书专属字段

每条商品代表**一本实物书**，独立展示和定价。

| 字段 | 录入方式 |
| --- | --- |
| 书名 | 必填 |
| 作者、出版社 | 填写或明确未知 |
| 版次 | 选择/输入；未知明确标注，不根据出版年份猜测 |
| ISBN | 可录入或明确无/未知；与版次分别保存 |
| 印次、出版或印刷年份 | 可选，分别显示，避免与版次混淆 |
| 适用课程、学院、专业 | 可选；与卖家个人所属学院分开 |
| 笔记 | 无、少量、较多、未知；可补充笔记方式 |
| 缺页 | 无、有、未知；有缺页需说明位置 |
| 附件 | 原无附件、附件齐全、附件缺失、未知，并写明内容 |
| 版权页、典型内页、缺陷图 | 可额外上传，鼓励提供，不强制所有卖家提供购买证明 |

信息尽量通过选项完成，降低发布负担。未提供版权页或证明时，不显示正版鉴定或保证。买家交付检查页提示核对书名、版次、笔记、缺页和附件。

**价格规则：用户提出过4元起价；本稿建议将4元作为定价提示，暂不设硬性最低价。是否强制4元下限仍属待定业务规则。**

### 7.3 搜索、详情和互动

支持关键词、分类、学院/专业、课程、版本、成色、交付方式和价格筛选；支持最新、价格等排序。按所选交付方式比较价格，避免以低商品价隐藏送货费。

商品卡片显示图片、标题、售价、交付方式和对应费用；例如“自提¥10 / 送货¥13”。免费商品如另收送货费，也须清楚显示。

详情展示原始介绍、所有图片、版本与缺陷、卖家公开资料、交付范围和时间。提供想要/私聊、出价、购买、点赞、收藏、分享、举报入口；点赞和收藏可取消。分享只包含公开信息，微信内具体分享能力需经过平台验证。

### 7.4 参考估价

首期可按品类、原价、购买时间、成色和书籍版本提供规则参考区间，展示主要依据；资料不足则不出估价。没有真实行情数据时，不标为准确市场价，不承诺收购价，也不让估价替代卖家自主定价。

## 8. 沟通、出价、合并下单和交付

### 8.1 私聊与出价

用户已允许买卖双方私聊，可询问物品、缺陷和交付。**买家出价，卖家接受或拒绝**；接受后才可按约定金额进入订单。私聊口头承诺不能直接改变订单价格。

订单明确商品价、送货费、平台服务费及总价。本稿将模拟版平台服务费设为0；真实收费规则需另行公布并确认。禁止要求订单外补款。

### 8.2 合并规则

同一卖家的多件商品可合并下单、一次取货或一次送货，书仍逐本计价。不同卖家分开成单。

本稿推荐沿用现有试用规则：**同卖家合并送货时，取所选商品送货费中的最高值，只收一次**；自提不收送货费。该具体算法应在正式运营前确认，并在订单提交前展示。

例：两本书分别10元、8元，各自送货费3元、5元；合并送货总价为10＋8＋5＝23元，而非26元。若商品不支持共同交付方式或同一时间，不应强行合并。

### 8.3 交付约定

买家选择自提或送货，填写可用公共地点和日期时段；卖家确认。下单后24小时内需确认交付安排，这与“24小时内必须实际交货”不同。

订单保存商品、价格、费用、地点和时间快照。改约要由另一方确认；待确认改约不能覆盖原约定。金额变化应通过明确的订单流程处理，不允许聊天补款。

## 9. 订单、计时和模拟账务

### 9.1 主流程

浏览商品 → 私聊或出价（可跳过） → 确认商品与交付信息 → 创建订单并锁定商品 → 模拟付款 → 确认安排 → 实际交接记录 → 买家确认收货或满足自动收货条件 → 模拟结算 → 评价。

| 状态 | 用户可见含义 | 主要操作 |
| --- | --- | --- |
| 待付款 | 商品短暂锁定，尚未模拟付款 | 付款、取消、超时关闭 |
| 已付款/待交付 | 模拟付款完成，等待安排或交付 | 确认安排、改约、符合规则的取消、售后 |
| 待买家确认交接 | 卖家已标记交付，买家尚未确认实际拿到 | 确认交接、确认收货、反馈未收到 |
| 待确认收货 | 买家确认实际交接，进入验收期 | 确认收货、售后、查看倒计时 |
| 已完成 | 已确认收货并完成模拟结算 | 评价、在规则期限内申请售后 |
| 已取消 | 未支付关闭，或取消并完成应有模拟退款 | 查看原因与记录 |
| 争议处理中 | 有有效售后争议 | 补充证据、协商、等待处理，暂停结算 |
| 已退款 | 模拟退款完成 | 查看处理结果和申诉入口 |

订单状态、交付状态、支付状态、退款状态、结算状态应分别保存，界面可简化展示。

### 9.2 三种计时必须区分

| 计时 | 建议或现有试用默认 | 规则状态 |
| --- | --- | --- |
| 待付款有效期 | 创建后30分钟未付款，关闭并释放商品 | 试用默认，正式运营前可调整 |
| 确认交付安排 | 下单后24小时内确认；已付款未确认的超时订单取消并模拟退款 | 用户要求24小时确认，超时处理按本稿默认 |
| 自动收货 | 买家确认实际交接后24小时，且无争议，才能自动完成和模拟结算 | 对原“24小时自动收货”的推荐细化，需最终确认 |

**不得从付款时间或卖家单方点击“已送达”开始无条件放款。**“确认实际拿到”与“确认商品验收完成”应分开。买家直接确认收货可以完成订单；买家报告未收到或发起争议时暂停自动结算。

买家一直不确认实际交接时，不无限推动自动放款，进入提醒或客服介入。正式运营前需进一步确定介入等待期限、证据规则和通知节奏。

超时任务在服务器执行，重启后仍能补处理；重复执行不得重复退款或结算。

### 9.3 取消、库存与并发

未付款可直接取消。已付款且未交付时按订单规则取消并退款；已发生交付后走售后。付款与取消同时发生、重复点击、多个买家争购时，结果必须一致，不能超卖或既退款又给卖家结算。

### 9.4 账务记录

支付、退款、结算、结算冲回分别记账，金额采用整数分；每条记录关联订单、时间、操作者、处理结果和唯一业务编号。对账以服务端账务与未来支付机构结果为依据，不能只看页面“成功”。

试用版所有相关页面和记录标明“模拟”，不得出现要求真实付款的二维码或转账指引。

## 10. 售后、客服和纠纷处理

### 10.1 受理范围

支持未收到、未按约定交付、版本不符、未说明缺陷、物品与描述不符、协商退货及其他反馈。

不承诺平台无条件包赔或所有二手物品无理由退货，也不写成“二手商品一律不能退款”。是否退款结合描述、约定、交付、证据和适用规则判断。

仅因不喜欢与明显描述不符分开处理；具体受理期限、退货费用承担和申诉期限需在真实交易前公开确定。

### 10.2 工单流程

选择订单/举报对象 → 选择原因 → 填写诉求并提交图文证据 → 双方回复和协商 → 客服处理 → 退款等结果执行 → 关闭或申诉复核。

工单状态至少包含待处理、处理中、待补充、待协商/执行、已关闭、申诉中。支持处理理由、时间线、相关订单、内部备注及用户可见回复。

处理结果可包括不退款、仅退款、退货退款、双方认可的部分退款。退款金额不得超过可退金额；涉及退货应记录退回与验收情况，不应由客服单方面承诺无法追回的款项。

### 10.3 客服工作台

显示每日08:00—20:00的服务时间；非工作时间仍可提交。是否真人在线须按实际值守显示。

工作台支持按类型、状态、时间筛选，领取或转派工单，查看必要证据与历史，回复、记录依据、提交处理结果和复核。客服不得处理自己的买卖或相关利益冲突工单。

平台内订单可申请平台流程处理。私下付款、私下成交没有平台支付退款能力，但仍可举报违规；不能用“仅提供平台”承诺免除所有责任。

## 11. 社区、群聊和私信

### 11.1 内容与分区

支持交流、求购、毕业闲置和校园互助帖子，支持评论、举报、屏蔽和点击用户进入公开主页查看在售商品。

支持本科、专科交流分区，以及学院/专业筛选；试点先开放计算机工程学院相关内容。毕业用户可参与，不强制提供学历证明。中专分区暂不开放。

### 11.2 总聊与学院群

广州校区总聊是所有注册用户可主动进入的公共频道。学院群每群最多500名有效成员；满员后创建下一序号群，例如计算机工程学院1群、2群。

不在注册时自动拉入所有群。加入、退出、重复请求和并发满员时名额必须正确；被限制的账号不能靠换群绕过处罚。总聊允许的成员数与服务器并发能力是两回事，不承诺无限承载。

群聊和私信需要保存历史、分页读取、发送失败提示、断线后恢复，以及举报和屏蔽。首期不要求音视频通话、直播或任意文件传输。

### 11.3 内容管理

群主与管理员按授权禁言、处理违规消息并保留依据。平台可处理诈骗、骚扰、广告、暴露隐私及禁售内容。推荐群主不等于投票即可获得全站权限；具体推荐与任期机制可后续细化。

## 12. 信誉积分、评价和违规处置

信誉满分100分，新用户默认100分；**低于60分不能发布新商品**。已存在订单仍应允许完成交付、退款和申诉，不能一封禁就失去售后入口。

只允许对有效完成订单评价，每个订单按规则限制评价次数。试用模拟订单的评价应明确为测试数据，不当作真实成交信用。

违规处理需关联事实、证据、规则和操作人员，可采取提醒、内容下架、限制曝光、限制发布或交易、扣分、封禁；各项限制分别记录。

点赞、收藏数、他人单次举报不能直接当作信誉担保，也不能仅凭举报自动扣分。重复举报同一事件不得重复处罚。用户可查看处罚原因、期限和申诉入口。

具体扣分档位、恢复规则与限流算法尚未确定，不将未经确认的数值直接写成自动处罚策略。

## 13. 真实支付与收费的后续边界

用户希望买家付款后，确认收货再让卖家获得货款。该目标应通过具备相应能力和资格的支付服务实现，不能简单把真实资金收进个人账户，再声称软件提供担保托管。

正式接入前需要核实：运营主体与平台准入、卖家收款资格、延迟结算或分账能力、退款与结算冲回、账单对账、异常处理及服务合同。产品不建设可充值或提现的自有钱包。

平台未来可收交易服务费等，但费率、收取对象、是否设最低收费、退款时是否退服务费，均待确定；最终费用需在下单前显示。

微信支付费用不能只回答一个固定百分比。可能包括支付通道手续费、平台服务方费用、认证费用及接入维护成本，取决于主体、产品和合同；**本稿没有核实当前官方报价，不作固定收费承诺**。模拟交易阶段支付通道费用为0。

## 14. 数据、运行与安全要求

### 14.1 核心数据

需要保存账号与公开资料、学校学院目录、商品和媒体、书籍字段、报价、订单快照、交付与改约、模拟账务、售后、帖子评论、群成员与消息、举报处罚、评价、审计及备份信息。

试用数据与演示数据隔离；禁止用共享演示账号处理同学的私人信息。数据库、上传图片、备份、密码和服务密钥不得提交到公开资源或代码仓库。

### 14.2 权限与安全

服务端逐次校验权限，不能只隐藏页面按钮。密码使用成熟的加盐哈希方案；敏感令牌不明文长期保存。认证和发送消息等接口需要限速，防止暴力尝试与刷屏。

公网部署使用HTTPS；限制跨站写入、脚本注入、路径越权和不安全上传。上传图片限制大小与像素；公开链接不能读到数据库、配置、备份或他人私密文件。

### 14.3 备份与恢复

至少每日备份数据库及关联图片，保留可恢复的一致快照，并设置保留数量和存储告警。定期在新目录恢复并确认账号、订单和图片正常，不能只检查备份文件存在。

正式运营前确定备份保留期、异地副本和恢复时限；测试备份不能覆盖真实运营数据。

### 14.4 稳定性与部署

网页和接口失败时提供错误和重试提示；后台任务异常可追踪。账号与图片应在正常重启后保留，避免使用会被平台自动清空的临时磁盘。

第一阶段采用小范围单实例试点，不宣称支持全学院同时在线。建议先按30名同时在线试用者验证浏览、消息和下单，再据真实结果定容量；该数字是待验证目标。

本地启动成功、GitHub保存代码、静态演示可打开、完整服务上线是四件不同的事。公网分享前必须确认完整后端、持久存储、HTTPS、管理员账号和隐私说明均有效。
