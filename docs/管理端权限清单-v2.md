## 1. 开源词库调研结论：**能借鉴，但解决不了你的两个核心需求**

我先去 GitHub 按你的思路找了现成的，结果需要如实说清楚——**词库和需求对不上**。

### 1.1 候选仓库与许可证筛选

| 仓库 | 许可 | 结论 |
|---|---|---|
| `fwwdn/sensitive-stop-words` | **Apache-2.0** ✅ | **采用**。Python 项目、124 KB、含"涉枪涉爆""色情类""广告"分类 |
| `konsheng/Sensitive-lexicon` | MIT ✅ | 许可可用，但主体是政治类与非法网址，与本模块用途无关，**未采用** |
| `houbb/sensitive-word` | Apache-2.0 | 是 Java 框架，算法思路可参考，词库形态不适配 |
| `cjh0613/tencent-sensitive-words` | **AGPL-3.0** ❌ | **传染性许可**，会波及整个发布物 |
| `cjh0613/strict-sensitive-word` | **AGPL-3.0** ❌ | 同上 |
| `57ing/Sensitive-word` | **无许可证** ❌ | 无许可 = 默认保留所有权利，**不能进发布物** |
| `fighting41love/funNLP` | **无许可证** ❌ | 同上，且仓库 174 MB |

许可证这一关就砍掉了 4 个（包括 star 数最高的两个）。这条筛查已写进 `scripts/fetch_wordlists.py` 的 `ALLOWED_LICENSES` 白名单，脚本遇到不在白名单的源会直接跳过。

### 1.2 但真正的问题是：内容对不上

我把采用的文件逐条看了，结论是**开源词库只覆盖"暴恐 + 低俗"，而你真正要的两件事它一件都不管**：

| 你的需求 | 开源词库里有什么 | 实际匹配度 |
|---|---|---|
| **反引流**（别把人导到微信/闲鱼） | `网址.txt` 14594 条，全是 `000.2011wyt.com`、`008.zhifong.cn` 这类**赌博色情小站域名** | **≈0**。学生的外流目标是闲鱼、转转、微信、QQ，这些域名一个都不在里面 |
| **禁售违禁品**（避孕套、刀具） | `涉枪涉爆违法信息关键词.txt` 437 条，内容是**「硝酸甘油炸弹制作」「黑火药的配方」** | **≈0**。这是"教人做炸弹"的词表，不是"卖刀具"的商品目录。整个 GitHub 上**没有**现成的电商禁售品清单 |
| 顺带的：广告词库 | `广告.txt` 123 条 | **不能直接用**。里面混着「**客服**」「网络」「到货」「**本店**」「代理」——"客服"在本站是完全合法的词，直接启用会大面积误伤 |

> 一句话：**开源社区做的是"内容审核词库"，你要的是"商品准入目录"，是两件事。**

### 1.3 所以最终方案是「自建为主 + 开源为辅」

| 词表 | 来源 | 条数 | 用途 |
|---|---|---|---|
| `prohibited_items.txt` | **自建** | 227 | 校园平台禁售清单（商品准入） |
| `diversion.txt` | **自建** | 62 | 交易外流检测（反引流） |
| `gunpowder.txt` | 开源 Apache-2.0 | 427 | 制爆暴恐类内容 |
| `vulgar.txt` | 开源 Apache-2.0 | 304 | 色情低俗内容 |
| **合计** | | **1020** | |

开源那两份**不提交进仓库**（体积 + 许可 + 上游会更新），由 `scripts/fetch_wordlists.py` 按需拉取，已在 `.gitignore` 排除。拉取时自动生成 `ATTRIBUTION.md` 记录来源、许可、sha256。

**政治类词库明确不纳入**：本模块只服务"违禁品审核"和"反引流"两件事，政治类词库与这两件事无关，但误伤面大、维护成本高。

## 2. 自动审核模块（已实现）

### 2.1 代码结构

```
Backend mission/app/moderation/
├── __init__.py                     对外 API：scan_text / scan_product / message_for
├── rules.py                        Aho–Corasick 自动机 + 词表加载 + 三级判定
└── data/
    ├── prohibited_items.txt        自建：校园平台禁售清单（227 条）
    ├── diversion.txt               自建：交易外流规则（62 条）
    └── thirdparty/                 开源词表（gitignore），脚本拉取
        ├── gunpowder.txt
        ├── vulgar.txt
        └── ATTRIBUTION.md
```

**为什么用 Aho–Corasick 而不是逐词包含判断**：朴素写法是「对每个词做一次 `word in text`」，1020 条词表下每次发布要跑上千次子串搜索；自动机的扫描代价只与**文本长度**相关，与词表规模无关——以后塞进几万条开源黑名单也不会拖慢发帖。纯标准库实现，无新增依赖（项目 `requirements.txt` 只有 Pillow）。

### 2.2 三级处置

| 级别 | 含义 | 动作 |
|---|---|---|
| **高** `block` | 法定禁止流通 / 明确的交易外流指令 | **拦截发布**，返回 422 + 命中说明 |
| **中** `review` | 平台限制类目 / 疑似联系方式 | **允许发布**，打 `moderation` 标记，进人工待审队列 |
| **低** `report` | 表达"想绕开平台"的意图 | 仅记录，不打扰用户 |

### 2.3 关键设计取舍

**① 词表里不收单字。**
只收「匕首」「弹簧刀」，**不收「刀」**——否则「剪刀」「水果刀」「《刀锋》」全部中招。这条由 `load_words()` 在代码层强制拦截，不是靠自觉。已写进测试。

**② 「当面交易」不能拦。**
本站是**同一校区**的二手平台，当面交付是正常且被鼓励的方式。要拦的是「把交易移出平台收款」，不是「线下见面」。所以只收「加微信」「走闲鱼」「扫码加」这类**明确的外流指令**，不收「线下交易」「当面交易」。

**③ 命中词不公开。**
`product()` 对外只暴露 `under_review` 这个布尔值，**不返回命中了哪个词**——公开了就等于把词表变成「哪个词会触发审核」的查询接口，等于教人绕过。卖家本人和客服/管理员能看到明细，便于申诉与处置。

**④ ISBN 只做词表检查、不走正则。**
ISBN 本身就是一长串数字，走「疑似QQ号」正则必然误伤。所以 `isbn` 字段单独走 `with_patterns=False`。

**⑤ 中危是"放行打标"不是"下架"。**
被打标的商品**照常出现在商品流**，只是卡片和详情页多一个「审核中」角标。这条有测试守着。

### 2.4 已接入的位置

- `CatalogService.publish()` —— 发布时审核。高危抛 `DomainError`（422），中危写入 `products.data.moderation`。
- `CatalogService.product()` —— 输出 `under_review`，并只对卖家/客服/管理员附带命中明细。
- 前端 —— 发布失败时 toast 显示拦截原因；卡片加「审核中」角标；详情页加复核提示条。

**尚未接入**（下一步）：聊天消息、社区帖子评论。规则引擎是通用的，接上去只是加几行调用。

### 3.2 B 类 · 平台限制（中 / 送人工审核）

成人用品（含**避孕套**）、烟酒、食品、化妆品个护、贴身衣物、保健品药品、宠物活体、预付卡与虚拟财产、**宿舍违规大功率电器**（电磁炉、电饭锅、热得快）、电池与出行工具、无人机与激光、**普通刀具**（菜刀、水果刀——合法但校园场景送审）。

### 3.3 ⚠️ 需要你确认的两处判断

1. **「避孕套」是平台自定禁售，不是法定违禁品。** 法律上它可以在药店合法销售。我们把它列为 B 类（送审而非拦死），理由是**二手贴身用品的卫生风险**和校园场景不适合。如果你希望改成直接拦死，改一个字段即可。同理，「防狼喷雾」「电子烟」也都是这个性质——**是平台规则，不是法律禁止**。

2. **「刀具」我做了分级，没有一律拦死。** 管制刀具（匕首、弹簧刀、弩）→ 拦截；菜刀、水果刀、厨刀 → 送人工审。因为后者是合法厨具，一刀切会让"毕业出个菜刀"这种事被拦。如果你要更严格（校园一律不许卖刀），我把 B 类那 4 条提到 A 类即可。

## 4. 客服界面：怎么"借鉴开源而不全部重写"

### 4.1 可借鉴的开源客服/工单系统

| 仓库 | 许可 | 借鉴点 |
|---|---|---|
| `django-helpdesk/django-helpdesk` | **BSD-3-Clause** ✅ | 许可最友好；工单队列的筛选维度设计 |
| `helpyio/helpy` | **MIT** ✅ | 许可最友好；"待办优先"的首页布局 |
| `frappe/helpdesk` | AGPL-3.0 | 界面现代（Vue），**只借鉴布局，不抄代码** |
| `uvdesk/community-skeleton` | OSL-3.0 | 工单属性面板 |
| `zammad/zammad` | AGPL-3.0 | 工单详情的「左侧会话流 + 右侧属性」经典布局 |
| `chatwoot/chatwoot` | 自定义许可（NOASSERTION） | 全渠道客服台的导航结构 |

**借鉴方式是「抄信息架构，不抄代码」**：这些系统是 Vue / Ruby / PHP，我们是原生 JS，代码层面本来也复制不过来。可借鉴的是它们沉淀下来的交互模式：

1. **列表页三件套**：状态标签 + 认领人 + 优先级，可筛选可排序（我们现在是全量平铺，没有筛选）
2. **详情页左右分栏**：左侧会话流、右侧属性面板（我们的工单详情已经接近这个结构了）
3. **快捷回复模板**：客服高频问题的预设话术
4. **批量操作**：勾选多行一起认领/结案
5. **时效高亮**：超时工单飘红

### 4.2 ⚠️ 许可证要分开看

- **只借鉴布局和交互** → 许可影响很小（不受版权保护的"想法"）
- **复制了代码/样式文件** → 必须遵守该仓库许可。**AGPL 和"无许可证"的仓库绝不能复制代码进来**

我们目前只做前者。如果后面想直接搬某个组件的 CSS，必须先确认许可。
