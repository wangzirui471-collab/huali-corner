# 转角：双人开发分工与验收任务书 V1.0

版本日期：2026-10-17。用途：两名开发者领取任务、约定接口、提交代码和联合验收。

本文是后续开发任务书，**不是功能完成报告**。本次只增加文档，没有改动业务代码。当前软件代码基线为 `b2fd4d2`；交接文档提交为 `1d30eab`。新任务从领取时双方确认的同一个集成提交开始，不能各自从不同旧 ZIP 开工。

## 1. 两人怎样分

| 负责人 | 第一批负责范围 | 第一批交付物 |
| --- | --- | --- |
| A：本项目协助开发者兼集成人 | 订单进度展示、模拟退款执行记录；公共接口接入与联合回归 | 订单/售后增量、B 模块接入、兼容检查和集成报告 |
| B：朋友 | 用户中心：学历与在读状态分离、头像、资料编辑与公开主页 | 独立用户领域代码、页面/组件/动作、迁移函数、测试与接入清单 |

这是按业务领域分工，每个人做自己领域的前后端，不是一个人改全部前端、另一个人改全部后端。B 先完成三个用户中心任务，不承担交易、客服资金或社区功能。

不同文件夹可以减少文本冲突，但不能保证业务没有冲突。例如 B 修改用户返回字段，可能影响 A 的订单卖家信息；修改相同数据库也可能互相覆盖。接口兼容、共享文件独占和联合测试仍然必须做。

两个人各自提交没有问题；冲突通常发生在合并或运行阶段。不要用“把对方的整个文件复制覆盖掉”解决冲突。

### 2.1 小程序边界

第一批 B 的验收对象是**共用后端＋网页用户中心**。小程序必须继续兼容原用户接口；本批不把小程序用户中心新功能算作已完成。

后续做小程序时，新建 `web 7M/miniprogram/features/user-profile.js` 和独立 `pages/user-center/`；公共页面注册、导航、请求工具由 A 接入，不把新功能继续塞进共用的 `pages/hub/`。微信开发者工具、真机和发布分别验收。

## 3. B 的第一批任务

完整说明见《用户中心开发任务书 V1.0》。先按 U01 → U02 → U03 顺序完成，每个任务一个可审查的提交。

| 编号 | 要完成的行为 | 核心验收 |
| --- | --- | --- |
| U01 | 将“学历层次”与“在读/毕业状态”分成两个选项，允许不填；保留旧账号资料 | 旧“已毕业”不能被猜成本科；保存不影响角色、信誉、手机号、密码和订单 |
| U02 | 用户上传、更换、移除头像；无头像时显示默认图形/昵称首字 | 校验图片内容与大小；不能使用别人的图片或证据图；只公开当前选中的头像 |
| U03 | 完善我的转角与公开主页，显示正确选项，保存反馈和冲突提示 | 手机可用；公开主页不泄露手机号和收货地址；切换账号不串资料；既有入口仍工作 |

暂不交给 B：短信、实名、支付、账号物理删除、批量数据导出、工作人员授权、信誉处罚、开通其他校区。后续的隐私请求入口可以另立任务，不在本批顺手做永久删除。

## 4. A 的第一批任务

以下是待开发范围，不宣称本次已实现，也不以修改整套状态机为起点。

### T01 订单进度可读化

在 `trade/progress.py` 增加订单进度投影；页面/动作放在订单对应模块，组件放在 `components/order-progress.js`。依据现有订单状态、交接记录和流水，分别显示订单、交付、售后、模拟资金进度及下一步操作人。

不能用一个“已完成”覆盖退款失败、退货中等情况；不能把卖家单方点交付当作买家已核对。投影只读，不产生扣款、退款或库存修改。

验收至少覆盖：待付款、待约时间、自提/送货、买家确认交接、售后暂停自动收货、取消退款、已完成后申请售后、买卖双方看到不同操作入口。若某个状态没有既有数据来源，应显示未知或待处理，不虚构已完成时间。

### T02 模拟退款执行记录与重复操作保护

在 `support/refund_execution.py` 组织“审核结论、模拟退款执行、流水核对”的区别，与 `trade/`、`ops/` 的原事务协作。先复用当前已有退款与幂等能力，补足缺口，避免另造一套余额账本。

验收：同一次执行重复提交只记一笔；权限与订单参与人冲突校验仍有效；执行失败不显示退款成功；重试不重复退款；退款、结算及冲回能够对账。这里始终是模拟资金，不能显示微信退款到账承诺。

### I01 B 模块接入与联合回归

A 负责迁移调用、Market 装配、HTTP 路由、媒体读取授权、旧用户接口兼容、前端动作/样式注册。每项记录接入位置并运行 B 的测试；避免把 B 的业务重写进公共入口。

暂缓部分退款到具体商品的分摊、送货费退款规则、真实支付：先列出计算例子和业务政策，再单独设计、开发与验收，不在本批擅自决定。

## 5. 统一编写规则

详细依据是《转角软件开发规范 V1.0》。对本批按以下规则执行；其中 `/api/v1` 新封装、全面框架迁移仍只是未来目标，不在此批改旧接口。

1. Python 3.12；Python 函数、变量、JSON 新字段用 `snake_case`，类用 `PascalCase`；JS 函数/变量用 `camelCase`，模块文件用 `kebab-case`。既有字段不随意改名。
2. 后端按 account/catalog/trade/support 等领域编写；入口只做解析、认证、调用与响应。前端页面渲染、组件和动作分层；共享可变状态只放 `core/state.js`，不得新增另一套登录状态。
3. 新 Python 代码使用 4 空格缩进、清楚的函数和必要类型标注；JS 延续现有 ES 模块格式，不新加框架或全局变量。不为统一风格批量格式化别人模块。
4. 现有接口返回形状、HTTP 错误和字段类型保持兼容；新接口与旧接口适配要明确。业务接口返回数据，不夹带 HTML；不提交堆栈、SQL 或令牌给客户端。
5. 金额为整数分，使用既有统一解析入口；本批新用户字段不涉及金额。数据库采用参数化 SQL、既有写事务和 DELETE 日志模式，不改全局连接策略。
6. 迁移只增量、可重复运行、能验证升级前后数据。不能删除数据库、重建账号或清空订单解决问题。
7. 权限由后端判定，不能只隐藏按钮；请求中的 `role`、`score`、`user_id` 不作为授权依据。跨账号缓存/异步回调必须校验当前会话，避免登出后写回前一个账号的数据。
8. 不记录密码、令牌、恢复码和私人图片；不把真实手机号、地址、学生表和运行数据库交入 Git。文件上传必须检验内容，不能只看扩展名。
9. 测试围绕用户行为、权限、兼容和失败路径；不能删除断言让测试变绿，也不能把 mock 成功称为真机或真实支付成功。
10. 用 Git 查第三方代码的许可证和来源；只采纳必要片段并说明，不复制无许可的完整项目，不引入与当前架构冲突的账号/支付系统。

## 6. 开工与接入方式

### 6.1 双方从同一提交开始

集成分支为 `feat/layered-completion`，它不是 `main`。A 先发布本文档，双方领取任务时记录同一完整提交号。朋友在自己的克隆目录执行：

```bash
git fetch origin
git switch -c feat/user-center origin/feat/layered-completion
git rev-parse HEAD
```

将输出写进自己的 `docs/modules/user-center/DELIVERY.md` 的“起始提交”栏。A 同期建立 `feat/trade-progress`，记录相同起点。上面的命令是朋友开工指南，本次没有替朋友创建或占用分支。

A、B 使用不同本地克隆和独立测试数据目录，不共享一个正在写入的 SQLite 文件。朋友需由仓库所有者添加私有仓库协作者；不要共享账号密码或访问令牌。

### 6.2 谁改公共文件

B 在 `INTEGRATION.md` 提交：新类与方法、迁移函数、路由/媒体钩子、前端导出、动作名/表单 ID、样式文件、兼容策略和验证命令。公共文件由 A 在集成分支接入，B 不自行编辑这些文件。

为使 B 能在自己的分支运行网页，A 在 U01 接口与导出清单稳定后先提供一个仅接线的提交，B 合入后再做 U02/U03。不能让 B 等到最后才发现页面根本未注册。若需要再次接线，按同样流程交给 A，不复制整个公共文件。

发现必须改对方独占文件：先记录原因、暂停该文件的并行编辑，确定临时负责人，再改。涉及资金或兼容合同的变动写清迁移和回滚影响，不用未经约定的接口将就。

### 6.3 提交与合并

- B 用 `feat(account): ...`、`test(account): ...` 等清楚的提交，推送 `feat/user-center`，向 `feat/layered-completion` 发 PR。
- A 的交易功能独立 PR；用户模块和订单模块不混进同一大提交。每个 PR 说明问题、行为、测试和限制。
- 合并前带入最新集成提交并解决冲突，重跑受影响测试。不要强推覆盖对方提交，不改 `main`，不上传整包 ZIP 覆盖代码。
- 朋友没有 GitHub 写权限时，可从分支导出 Git patch 供 A 审查；仍需完整提交来源和文件清单，不能仅发截图。

## 7. 最终交付准则

### 7.1 B 可以提交审查的条件

U01/U02/U03 功能、专属测试、增量迁移、接口例子和接入清单齐全；未接线部分写明由谁接、接在哪里。模块测试通过只代表可以审查，**不等于整个软件验收完成**。

### 7.2 双方集成后的完成条件

- 网页实际注册、登录、编辑、刷新、换账号、公开主页查看均通过；资料保存失败有明确提示，不无限转圈。
- 原账号、订单、草稿、图片、信誉和角色保留；小程序旧接口兼容。用旧数据的副本验证，不操作同学唯一一份实际数据。
- 未登录访问、越权修改、头像证据越权、重复提交、并发修改、页面脚本注入等失败场景有测试；页面隐藏不能代替服务端拒绝。
- 375/390/768/1440 宽度下可用，没有整页横向溢出、遮挡主按钮和新控制台错误；默认头像和空资料可用。
- 原项目 Python 测试、Node 逻辑/模块测试及相关浏览器流程通过；注明实际命令、日期、环境、结果、未运行项和原因。
- 源码交付含完整模块、资源、迁移和测试，不含数据库、上传照片、备份、口令与私人配置；可从新目录按文档启动。
- PR 附修改文件清单、提交号、界面截图、升级说明、回滚注意事项及已知限制。若有新的数据写入，回滚不能靠盲目覆盖整库让它们丢失。

### 7.3 本批不接受的“完成”

只有效果图；仅代码能 import；所有场景依赖假成功接口；为了升级要求用户重新注册；把毕业生误判为学生认证；实机未测却说微信通过；未接支付却说托管到账；关键接线未做却标记全软件完成。
