## 2. 已复现、尚未修复

### F-01 高：被封禁卖家的预留商品重新回到商品流，还能再次下单

- 复现：卖家发布 → 买家创建待付款订单 → 管理员封禁卖家。
- 实际：订单取消后，`release()` 将商品重新设为 `available`；商品再次出现在公开流，新买家仍能生成待付款订单。卖家账号保持 `banned`，无法正常履约。
- 原因：封禁流程先下架 `available` 商品，随后取消预留订单时无条件释放库存；下单也没有核验卖家启用状态。
- 位置：`Backend mission/app/support/service.py` 的 `ban_user/_settle_banned_orders`，`app/trade/service.py` 的 `release/checkout`。
- 建议与验收：释放前检查卖家状态；被封禁 / 注销 / 停用卖家的物品继续保持下架，商品流和结算再设防线。补待付款、超时、取消及卖家恢复状态的测试。

### F-02 高：发布内容没有草稿自动保存

- 复现：进入发布页，填写标题和介绍，刷新页面；或离开后重新进入。
- 实际：标题和介绍均为空。三张图片也只保留在当前表单，未提交前没有草稿持久化。
- 位置：`web 7M/src/pages/publish.js`、`src/actions/catalog.js`；未发现商品草稿的保存 / 恢复实现。
- 建议与验收：按账号自动保存文字和照片，展示保存状态；重新打开可继续编辑，成功发布后清除对应草稿，切换账号不串数据。需要明确本机草稿与跨设备草稿的边界。

### F-03 高：卖家停留在首页，新订单不会主动更新角标

- 复现：卖家登录并停留首页；独立买家下单并模拟付款；等待 18 秒。
- 实际：后台已有 2 条未读通知，订单能查到，首页角标仍隐藏。`refreshBadges()` 只在路由渲染等操作调用，没有全站定时刷新。
- 位置：`web 7M/src/core/badges.js` 和路由调用。
- 建议与验收：增加全站通知刷新或事件推送，覆盖新订单、付款、售后；两账号测试停留首页也能及时获知。手机锁屏通知是另外的能力，需要 HTTPS、权限申请及适配；当前未实现系统推送，站内消息不等于手机推送。

### F-04 中：非书商品发布仍展示整段二手书字段

- 复现：发布页选择“宿舍生活”。
- 实际：版次、出版社、笔记、缺页等书籍字段仍然显示。后端没有强制非书填写这些字段，因此是发布负担，不能说非书完全无法发布。
- 建议与验收：按分类显示必要字段；书况提供可选模板与待确认选项。书籍切换到闲置后，界面与提交数据都应一致。

## 4. 测试结论与边界

- 合并上游及数据库修复后：全量 **288/288 项通过**，包括本轮新增 4 项适配器回归、1 项共享 HTTP 与重启回归，以及上游新增 1 项本机 / 局域网 Origin 回归。
- 前端：41 个模块可加载且依赖无环；3 个 Node 测试文件通过。
- 浏览器：注册、发布三图、收藏、下单、模拟付款、权限、改密、恢复码与会话失效通过；商品上下架权限与四档视口既有冒烟通过。
- 额外共享检查：独立浏览器 / HTTP 客户端共用后端可互相看到商品、图片和订单；重启后仍保留。独立数据目录互不共享。
- 未完成：真实公网部署、两台实体设备与校园网络连通性、MySQL 实例集成、微信小程序开发者工具 / 真机、锁屏推送、真实短信和支付、持续压力及故障恢复演练。

以上通过项不能覆盖 F-01—F-04；它们是在既有测试外额外复现的问题。下轮优先顺序建议：F-01 → 集中部署验收 → F-02 / F-03 → F-04；MySQL 等双引擎验收完成后再启用。
