# 后端评估与迭代建议

日期：2026-10-18。依据当前 Windows 项目 `08db9f8` 的代码检查、仓库需求 V1.3、用户提供的需求 V1.2 与开发规范 V1.0。下列建议不是已交付功能清单，也不是新增需求已获全部实施授权。此轮仅整理文件。

平台已有注册登录、商品发布、报价、订单、模拟账本、售后、聊天、人员角色、审核、通知和备份。下一阶段应优先补齐可靠性与流程闭环，再加更多展示功能。

## 已有能力不重复建设

| 能力 | 当前代码依据 | 仍需关注 |
| --- | --- | --- |
| 独立客服和管理员账号 | `app/staff/service.py`、`roles.py` | 工单权限应与指派、利益冲突和审批职责联动 |
| 工单与客服会话认领 | `support/service.py:resolve_ticket`、`community/service.py:claim_support_room` | 竞争认领、交接、超时待办及审批轨迹需要完整验收 |
| 订单与售后通知 | `trade/service.py:notify/notifications/read_notifications` | 补客服待办提醒、交接提醒和可靠投递记录，不能称通知完全未做 |
| 交易防重复 | `trade/service.py:checkout` 按用户与 request_key 复用订单 | 商品发布仍需独立幂等语义；跨进程及 D1 并发需另外验证 |
| 内容审核和商品管理 | `moderation/`、`catalog/service.py` | 关注申诉、复核及不同角色的边界 |
| 对账和备份 | `ops/service.py` | 备份创建不等于恢复演练通过，也不是异地备份 |

## 建议的功能顺序

| 优先级 | 建议补齐 | 学生或工作人员能得到什么 | 后端落点与验收 |
| --- | --- | --- | --- |
| P0 公开试用前 | 交易竞争与账号限制的统一校验 | 被限制的卖家不会通过取消、超时或重新上架重新进入可交易状态 | `catalog/`、`trade/`、`account/`；使用不同用户和请求键竞争单件商品，叠加封禁与取消，验证只有有效的一方成功且账本守恒 |
| P0 公开试用前 | 工单认领、复核、退款审批形成明确职责链 | 谁处理、谁批准、为什么退款可追溯，客服不能处理自己的交易 | `support/`、`staff/`；验收并发认领、越权、利益冲突、重复批准和退款失败回滚；审批分权目标需先核对现有业务确认记录 |
| P0 公开试用前 | 可恢复的备份、运行故障记录与任务状态 | 数据丢失可恢复，后台任务失败能定位并重试 | `ops/`、`core/`；恢复到空目录比对合成账号、图片、订单和账本；提供去敏请求编号、备份状态和定时任务最后成功记录 |
| P1 发布体验 | 服务器草稿与版本控制 | 发到一半退出后能继续，多窗口不会静默覆盖 | `catalog/drafts.py` 等领域内模块；按账号隔离，版本冲突返回 409，断网重试不泄露其他账号草稿；保留期按隐私规则确定 |
| P1 发布体验 | 发布幂等与在售商品编辑 | 网络超时重试不重复发布，卖家可修正文案和价格 | `catalog/`；同账号同键返回同件商品，不同请求内容冲突；预留、售出和被管理下架的商品不能绕过校验，旧订单快照不随编辑改变 |
| P1 售后闭环 | 实物退回确认与重售草稿 | 只有确实拿回商品且退款、争议结束后才能再次出售 | `support/`、`catalog/`；仅退款、退货在途、争议中均不能恢复，重复确认不生成两件在售实物 |
| P1 工作台效率 | 待办中心、可靠提醒与交接 | 客服能看到待认领、待补证、待复核、超时事项 | 扩展现有通知与工作台；未读按账号和事件计算，已处理事项不重复提醒，通知失败不回滚已提交的业务交易 |
| P2 试点扩大后 | SQL 分页、筛选、索引与查询统计 | 商品和消息增多后仍可用，管理列表不会一次读取全库 | `catalog/`、`community/`、`support/`；现有商品列表部分筛选与分页仍在 Python，迁移时保持旧返回合同，使用合成数据与查询计划验证 |
| P2 运营完善 | 隐私生命周期与处罚申诉冲回 | 用户知道如何申请停用或删除，错误处罚可以按原记录冲回 | `account/`、`support/`、`ops/`；交易证据保留与可删除资料分开，冲回不能重复加分，期限与恢复规则待确认后启用 |

P0 的限制校验来自已有设计中已记录的问题及本次代码检查，不能在没有针对性复现前把每项都称为新确认漏洞。工单链已经存在认领和审核状态，建议补的是并发、职责和审计闭环，不是另建一套工单。

## 分层实施原则

新能力进入相应领域，入口层负责解析、认证和路由。已有 `Market` 组合方式保持；不借整理迁移 FastAPI、重命名金额字段、全站套 API 封套或一次性拆散现有服务。草稿、编辑、售后重售和审批分别设计与验收，每批只改必要模块。

Cloudflare 异步 D1、R2、密码 Web Crypto 与定时触发属于部署适配工作，需要共同保持权限、库存、账本和幂等规则；本机 HTTP 服务已恢复不代表云端应用已发布。先完成依赖可重复构建和 D1 原子性证明，再开放真实可注册的云端试用。

## 当前不急于加入

真实支付或提现、自建钱包、自动赔付、短信认证、复杂推荐算法、微服务和多服务器集群暂不作为本轮目标。当前仍是模拟交易的小范围学院试点；信誉自动处罚、费用和保留期限不能仅因建议文档出现就自动启用。


## 本轮检查发现的测试工程问题

完整 Python 回归共 294 项，287 项通过、7 项报错，未实现“全量通过”：1 项静态路径测试因 Windows 缺少创建符号链接的权限而报 WinError 1314；5 项降权测试在清理临时 SQLite 文件时遇到 WinError 32；1 项可移植降权命令测试因子进程输出编码不一致而无法取得文本。

代码检查发现降权测试在 setUp、query 及备份检查中使用 `with sqlite3.connect(...)`，它控制提交回滚但不保证关闭连接；生产降权模块已有 `contextlib.closing`。因此应优先修正测试的显式资源释放和 UTF-8 子进程约定，再在具备符号链接能力的测试环境补齐路径逃逸验收；本次没有修改这些测试或生产模块，也没有关闭权限检查来伪造通过。
