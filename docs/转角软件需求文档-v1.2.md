## 1. 产品定位与目标

转角是面向校园的二手交易与交流平台，帮助学生、毕业生出售闲置物品，让有需求的同学以较低成本购买，并通过平台订单、交付记录和售后渠道减少交易纠纷。

首批从广州华立学院广州校区的**计算机工程学院**试点，先覆盖少量专业、真实卖家和真实求购需求。商品以**逐本二手书、宿舍日用品、运动闲置、电子产品**为主，暂不以高价数码或奢侈品为核心。

产品希望完成三个基本结果：

1. 卖家能方便、如实地发布物品，买家能看清版本、缺陷、价格和交付方式。
2. 双方能在平台内沟通、出价、下单、约定交付，并在发生问题时留有可核查的记录。
3. 校园社区帮助同学交流、发布求购和认识其他卖家，但社区热度不作为交易信用担保。

### 1.1 已确定的经营约束

| 项目 | 要求 |
| --- | --- |
| 运营者 | 个人试做，当前没有公司主体 |
| 试做预算 | 人民币3,000元；不得将该预算理解为已经购买服务 |
| 首期地域 | 广州校区，优先计算机工程学院试点 |
| 注册资格 | 不要求学生证明或实名认证，毕业生可以使用 |
| 首期登录 | 手机号＋密码；不发送短信，手机号归属暂未验证 |
| 交易 | 模拟支付、模拟退款、模拟结算，不收取真实货款 |
| 客服时间 | 每天08:00—20:00，中国标准时间 |
| 品牌 | 统一使用"转角"；旧名称"华立转角"需要逐步替换 ❌ 尚未执行 |

### 1.2 试点成效

观察注册人数、真实有效商品数、求购响应、模拟下单完成率、取消原因、纠纷原因和客服处理时间。模拟成交量必须与未来真实成交量分开统计，不将测试数据当作平台业绩。

首轮建议邀请10—30名同学，完成至少5组买卖双方的完整试用，再决定是否扩大范围。这是试点建议，不是已完成的运营成果。

## 5. 账号、资料和隐私

### 5.1 注册与登录 ✅

1. 使用手机号和密码注册，昵称必填；展示手机号暂未验证的说明。
2. 不要求身份证、学生证、学号、学校邮箱或人脸材料。不将用户标为"实名""本校认证"。
3. 手机号不可重复注册；密码不得明文存储。当前试用规则为12—128字符。
4. 支持登录、退出、修改密码和安全恢复；连续错误尝试应限速或暂时锁定。
5. 无短信验证时，账号恢复需恢复码，不能仅输入手机号重置他人密码。
6. 改密或恢复后使旧会话失效。注册或登录失败应给出可理解的原因，避免无限转圈。

**实现要点**：密码使用加盐哈希；恢复码仅在生成时展示一次；登录失败 5 次锁定 15 分钟；改密或恢复后清除全部会话。

### 5.2 个人资料 ✅

可填写头像、昵称、学校、学院、专业、就读层次或毕业状态、个人介绍。学校及学院资料为自愿填写的资料，不是身份认证；未填写不阻止基本注册。

就读层次与毕业状态应分开表达，避免把"已毕业"当作一种学历。首期面向本科、专科及毕业用户；暂不建立中专市场和中专社区。

首期界面突出计算机工程学院试点，不能宣称已验证访问者的学院身份。后续学院扩展不应要求重新注册账号。

### 5.3 数据可见范围 ✅

| 数据 | 可见范围 |
| --- | --- |
| 商品标题、价格、商品图、公开介绍 | 可公开浏览 |
| 昵称、自愿公开的学院与专业、在售商品 | 公开主页可见 |
| 手机号、恢复信息、私人购买凭证 | 不出现在公开页面和公开接口 |
| 私聊 | 相关双方；投诉调查按授权和告知规则处理 |
| 订单交付详情 | 交易双方及有业务需要的授权人员 |
| 售后证据与内部处理记录 | 相关用户按权限查看，内部备注不公开 |

注册和上传时说明数据用途。对外试用应提供隐私说明、账号停用及删除申请渠道，并说明依法或为争议处理需要保留的记录。

**重要**：`var/` 与 `var-trial/` 已在 `.gitignore` 中排除，不进入版本库。提交前应确认 `git ls-files` 输出中不含这两目录 —— 参见 14.1。

### 7.6 下架与重新上架 ✅ 本轮新增

> V1.1 第 16.2 节 A22 提到"重新上架"是针对**退货售后**的场景。本节描述的是**卖家主动下架**，两者的状态流转规则不同，不要混用。

**功能定位**：卖家挂上商品后，可能需要临时收起（自己还想留着、暂时不想卖、要改价重发）。下架不是删除，随时可以恢复。

**接口**

| 接口 | 方法 | 参数 | 说明 |
| --- | --- | --- | --- |
| `/api/my-products` | GET | `?status=removed` 可选 | 返回卖家自己的全部商品，**含已下架** |
| `/api/product/status` | POST | `{id, action:'delist'\|'relist'}` | 下架／重新上架 |

**状态流转规则**

| 当前状态 | 可下架 | 可重新上架 | 原因 |
| --- | --- | --- | --- |
| 在售 available | ✅ | — | 正常在售，可随时收起 |
| 已下架 removed | — | ✅ | 回到在售 |
| 已预留 reserved | ❌ | ❌ | **该商品已挂在某张待付款订单上**，下架会让那张订单指向一个消失的商品 |
| 已售出 sold | ❌ | ❌ | 交易已完成 |

**权限**：只有商品所属卖家可以操作自己的商品；他人操作返回 403。

**为什么不复用 `products()` 接口**：`products()` 会把 `removed` 的商品过滤掉（这是对的，买家不该看到），但卖家需要在"我发布的"里看到自己下架的东西，所以另开了 `my_products()`。

**界面**：`#listings` 路由（网页）／hub 页"我发布的"标签（小程序）。按状态分组展示，顶部有在售／已下架／已预留／已售出的数量统计。下架与上架按钮带二次确认。

**未做**：下架后的商品不计入任何统计分母；管理员也看不到"某卖家下架了多少件"，这个运营视角尚未实现。

## 8. 沟通、出价、合并下单和交付

### 8.1 私聊与出价 ✅

用户已允许买卖双方私聊，可询问物品、缺陷和交付。**买家出价，卖家接受或拒绝**；接受后才可按约定金额进入订单。私聊口头承诺不能直接改变订单价格。

订单明确商品价、送货费及总价。模拟版平台服务费为 0；真实收费规则需另行公布并确认。禁止要求订单外补款。

### 8.2 合并规则 ✅

同一卖家的多件商品可合并下单、一次取货或一次送货，书仍逐本计价。不同卖家分开成单。

**同卖家合并送货时，取所选商品送货费中的最高值，只收一次**；自提不收送货费。该算法在订单提交前展示。

例：两本书分别10元、8元，各自送货费3元、5元；合并送货总价为10＋8＋5＝23元，而非26元。✅ 已按此实现。

### 8.3 交付约定 ✅

买家选择自提或送货，填写可用公共地点和日期时段；卖家确认。下单后24小时内需确认交付安排，这与"24小时内必须实际交货"不同。

订单保存商品、价格、费用、地点和时间快照。改约要由另一方确认；待确认改约不能覆盖原约定。✅

## 9. 订单、计时和模拟账务

### 9.1 主流程 ✅

浏览商品 → 私聊或出价（可跳过） → 确认商品与交付信息 → 创建订单并锁定商品 → 模拟付款 → 确认安排 → 实际交接记录 → 买家确认收货或满足自动收货条件 → 模拟结算 → 评价。

| 状态 | 用户可见含义 | 主要操作 |
| --- | --- | --- |
| 待付款 | 商品短暂锁定，尚未模拟付款 | 付款、**修改订单**、取消、超时关闭 |
| 已付款/待交付 | 模拟付款完成，等待安排或交付 | 确认安排、改约、符合规则的取消、售后 |
| 待买家确认交接 | 卖家已标记交付，买家尚未确认实际拿到 | 确认交接、确认收货、反馈未收到 |
| 待确认收货 | 买家确认实际交接，进入验收期 | 确认收货、售后、查看倒计时 |
| 已完成 | 已确认收货并完成模拟结算 | 评价、在规则期限内申请售后 |
| 已取消 | 未支付关闭，或取消并完成应有模拟退款 | 查看原因与记录 |
| 争议处理中 | 有有效售后争议 | 补充证据、协商、等待处理，暂停结算 |
| 已退款 | 模拟退款完成 | 查看处理结果和申诉入口 |

订单状态、交付状态、支付状态、退款状态、结算状态分别保存，界面可简化展示。⚠️ 当前界面仍以单一状态文本呈现。

### 9.2 三种计时必须区分 ✅

| 计时 | 现有试用默认 | 规则状态 |
| --- | --- | --- |
| 待付款有效期 | 创建后30分钟未付款，关闭并释放商品 | 试用默认，正式运营前可调整 |
| 确认交付安排 | 下单后24小时内确认；已付款未确认的超时订单取消并模拟退款 | 用户要求24小时确认 |
| 自动收货 | 买家确认实际交接后24小时，且无争议，才能自动完成和模拟结算 | 待最终确认 |

**不得从付款时间或卖家单方点击"已送达"开始无条件放款。**"确认实际拿到"与"确认商品验收完成"应分开。买家直接确认收货可以完成订单；买家报告未收到或发起争议时暂停自动结算。✅ 已按此实现。

超时任务在服务器执行，重启后仍能补处理；重复执行不得重复退款或结算。✅

### 9.3 取消、库存与并发 ✅ 本轮修复

未付款可直接取消。已付款且未交付时按订单规则取消并退款；已发生交付后走售后。

**付款与取消同时发生、重复点击、多个买家争购时，结果必须一致，不能超卖或既退款又给卖家结算。**

> ⚠️ **本节曾存在实现缺陷，本轮已修复。** 详见 14.5。
>
> 修复前：三个线程并发抢同一件商品时，**偶尔会有两个买家同时下单成功**（真实重复售卖）。
> 修复后实测 20 轮，每轮都恰好 1 人成功。核对方式见 14.5。

### 9.4 账务记录 ✅

支付、退款、结算、结算冲回分别记账，金额采用整数分；每条记录关联订单、时间。✅

对账以服务端账务为依据（`/api/reconcile`），不能只看页面"成功"。✅

试用版所有相关页面和记录标明"模拟"，不得出现要求真实付款的二维码或转账指引。✅

### 9.5 付款前修改订单 ✅ 本轮新增

**功能定位**：买家下单后、付款前，可能发现选错了交付方式、填错了地点、约错了时间，或者临时不想买其中一件。这时候双方都还没投入成本（买家没付钱、卖家没打包），改起来没有风险。

付款之后不适用本节，改时间要走原有的"申请改约"（需对方确认）。

**接口**

```
POST /api/order/update
{ id, product_ids?: [...], delivery?: 'pickup'|'delivery', address?: str, appointment?: ts }
```

**可改内容与权限**

| 字段 | 买家 | 卖家 | 说明 |
| --- | --- | --- | --- |
| `product_ids` 移除商品 | ✅ | ❌ | 传保留的商品 id 列表；未保留的会被移除 |
| `delivery` 交付方式 | ✅ | ❌ | 改成送货会重算送货费 |
| `address` 收货地点 | ✅ | ❌ | 送货时必填；自提时自动清空 |
| `appointment` 交付时间 | ✅ | ✅ | 双方都可改，须在 60 秒后至 30 天内 |

**状态前置条件**：仅 `awaiting_payment`。已付款调用返回 400，提示改用"申请改约"。

**移除商品的连带处理**（这是本节最容易出错的地方）

1. 被移除的商品从订单 `items` 中删除
2. 该商品状态从 `reserved` 释放回 `available`，重新出现在公开列表里
3. 重算 `subtotal`（剩余商品价格之和）
4. 重算 `delivery_fee`（若为送货，取剩余商品送货费的最高值；若为自提则为 0）
5. 重算 `total = subtotal + delivery_fee`
6. 在 `order_notes` 表记录"买家移除商品：XXX"，供事后追溯

**边界校验**

- 订单至少要保留一件商品，全部移除返回 400
- 传入的 `product_ids` 必须都属于本订单，否则返回 400
- 改成交付方式后，订单内所有商品都必须支持该方式，否则返回 400
- 非订单当事人调用返回 403

**界面**：订单卡片上"修改订单"按钮（仅待付款状态显示，买卖双方都可见）。弹窗内可勾选/取消勾选商品，选择交付方式、填写地点、选择时间。取消勾选的商品在弹窗里会变灰，保存前就能看出会移除哪些。

**小程序**：原生端用 `wx.showActionSheet` + `wx.showModal` 走"交付方式 → 地点 → 时间"三步。⚠️ **小程序端不支持移除订单内商品**（原生弹窗难以承载勾选列表），需要该操作请用网页端。

### 9.6 卖家取消订单 ✅ 本轮新增

V1.1 原文只允许买家取消。本轮放开给卖家，但**仅限买家付款前**：

| 调用者 | 订单状态 | 是否允许 |
| --- | --- | --- |
| 买家 | 待付款 / 已付款 | ✅ |
| 卖家 | **待付款** | ✅ 本轮新增 |
| 卖家 | 已付款及以后 | ❌ 提示走客服流程退款 |

理由：卖家在买家付款前取消不涉及资金；付款后由卖家单方取消会产生退款责任，应走客服流程留痕。

## 10. 售后、客服和纠纷处理

### 10.1 受理范围 ✅

### 14.5 数据库并发写入规则 ✅ 本轮修复（新增章节）

> 本节记录一个**已修复的真实缺陷**与随之确立的实现约束。改动 `Backend mission/db.py` 前必读。

**修复前的缺陷**

| 现象 | 影响 |
| --- | --- |
| 并发写入时随机抛 `sqlite3.OperationalError: attempt to write a readonly database` | 30 并发写约 2–5 次失败，接口返回 500 |

根因：本项目写法是"每次事务新开连接、用完即关"，而 SQLite 的 WAL 模式下**最后一个连接关闭时会自动 checkpoint 并删除 `-wal` / `-shm` 文件**。此刻另一个线程刚开好连接准备写入，找不到 wal 文件即报"只读数据库"。

**修复**

不使用 WAL，改用默认的删除日志模式：在 `app/core/database.py` 初始化时执行一次 `PRAGMA journal_mode=DELETE`，同时把旧库迁出 WAL。该 pragma 绝不能放进 `connect()` 每次连接都执行 —— 它需要短暂的独占锁，多线程同时执行会互相冲突。

**两处曾被写错、现已更正的说法**

1. **没有发现真实超卖。** 早期一次并发测试里出现"两人下单成功"，排查后确认是测试用例复用了
   **同一个幂等 key**，两个线程拿到的是同一张订单 —— 这恰恰是幂等设计想要的结果，
   并不是一件商品卖给了两个人。改用各自独立的 key 重测：3 线程抢同一件商品，
   加不加写锁都是 0 次超卖。真正挡住超卖的是 `checkout` 事务内的库存状态校验，不是下面那把锁。
2. **写锁不是这次修复的关键。** 切到 DELETE 日志模式之后，30 并发写 × 5 轮，
   加锁与不加锁都是 0 失败 —— 真正解决问题的是换日志模式。
   `app/core/database.py` 里的 `_WRITE = threading.RLock()` 仍然保留，
   作用是让写事务串行、避免多线程交叉持有 `BEGIN IMMEDIATE`；
   但**不要把它当成并发安全的保证**：它只在单进程内有效，多进程部署或将来的真实数据库都不成立，
   库存正确性仍要靠事务内的状态校验。

**验证结果**

| 场景 | 结果 |
| --- | --- |
| 30 线程并发写 × 5 轮 | 0 / 150 失败 |
| 3 线程并发抢同一商品（各自独立幂等 key）× 20 轮 | 20/20 轮恰好 1 人成功，0 次超卖 |
| 20 线程并发读 | 0 失败 |

对应测试：`tests/test_market.py::test_concurrent_checkout_one_winner`
（改为按数据库中的订单条数与不同订单号计数来断言，不再被幂等返回干扰）、
`tests/test_market.py::test_concurrent_checkout_distinct_keys_no_oversell`。
