## 3. U01：资料选项分开、历史数据保留

### 3.1 用户能做什么

学历层次与在读状态分开选择，可以不填；昵称、专业、简介仍可编辑；网页选项真实回填，保存失败保留已输入内容。学院试用模式仍按现有规则固定计算机工程学院，不因此开放其他校区或冒充学校身份核验。

新字段合同：

| 字段 | 类型与允许值 | 说明 |
| --- | --- | --- |
| `degree_level` | 字符串：`bachelor`、`junior_college`、`other`、`unspecified` | UI：本科、专科、其他、暂不填写 |
| `study_status` | 字符串：`studying`、`graduated`、`other`、`unspecified` | UI：在读、已毕业、其他、暂不填写 |
| `profile_version` | 非负整数 | 仅资料修改递增，用于阻止旧页面覆盖新资料 |
| `avatar_upload_id` | 字符串或 `null` | 仅引用当前账号通过头像校验的资源 |
| `avatar_url` | 服务端生成的本站路径或 `null` | 只读；不能由客户端填写外部 URL |

继续保留原 `id`、`nickname`、`college`、`major`、`education`、`bio`、`role`、`score` 的类型和含义，不换 ID，不让资料更新写角色或信誉。`role`、`score` 可按原合同返回，但客户端不可修改。

### 3.2 历史 education 怎么处理

迁移前检查列是否存在；已有新字段不重复覆盖。迁移规则：

| 旧 education | 新 degree_level | 新 study_status |
| --- | --- | --- |
| 本科 | `bachelor` | `unspecified` |
| 专科 | `junior_college` | `unspecified` |
| 已毕业 | `unspecified` | `graduated` |
| 其他或未填写/未知值 | `unspecified` | `unspecified` |

旧原值保留，不猜测未知学历或在读状态。新客户端保存时，旧 `education` 兼容投影：已毕业优先显示“已毕业”；否则按本科/专科层次显示；其余显示“其他”。这只是旧客户端的简化展示，新字段才是完整选项。

旧客户端通过 `/api/me` 保存资料时：原昵称、学院、专业、简介按原规则处理；只有旧 `education` 明确提供且相对当前兼容值改变，才按上表调整新选项；相同值不覆盖新字段。不能因旧客户端未带 `study_status` 就清空它。所有资料写入路径均更新资料版本；涉及老接口版本缺失的兼容限制写进交付说明。

### 3.3 写权限与冲突

新资料提交必须带 `profile_version`，在同一个事务内比对并递增；旧版本返回 409，页面提示重新载入/核对，不静默覆盖。新客户端可修改字段：昵称、专业、简介、学历层次、在读状态；头像走专用接口。学院沿既有试用约束，由服务端确定。

昵称非空、最多24字符，专业最多80，简介最多300；超长明确报错，不悄悄截断。枚举错误、负数/布尔类型的版本号拒绝。新接口遇到手机号、密码、用户 ID、角色、信誉等未允许字段时拒绝，不能展开 payload 直接更新数据库。

## 4. U02：头像上传、更换与移除

- 支持真实 JPEG/PNG/WebP 图片，单次原文件不超过 2 MiB；解码前设像素上限1600万，拒绝损坏图片、SVG、动画、多帧图片和解压炸弹。
- 对 EXIF 方向做校正，清除原 EXIF/GPS 等元数据；在服务端生成最长边不超过512像素的静态 WebP。网页允许预览，最终校验不能只靠前端。
- 文件名由服务端随机生成，路径由既有配置/数据根取得，放入运行数据的 `uploads/`，不放源码或静态资源目录。不接受客户端路径或外部头像下载 URL。
- 上传和设为头像分开：上传成功只供本人预览；带资料版本确认选中后，才成为公开头像。未选中的头像不能通过猜 URL 被未登录者读取。
- 选择时核对所有者、资源用途为头像、实际文件存在；不能借用商品照片、别人的上传、私密工单证据。移除头像后回到默认显示。
- 替换/移除后旧头像取消“因当前头像而公开”的权限；不能顺手删除被其他合法记录引用的照片，也不急着物理清理所有历史图片。
- 上传头像不能修改 `role`、`score`、订单和商品。上传响应不得返回本机路径。

原 `/api/upload` 只支持商品/证据图，不直接扩大其用途去绕过原校验。新增头像专用逻辑；媒体公开读取权限是 A 接入的关键点，必须给出 `user_is_public_avatar(upload_id)` 判定方法并测试。

## 5. 供 A 接入的接口合同

以下为**本任务的拟新增合同**，当前代码尚无这些路由。方法由你实现，A 在 U01 合同确定后接线。保留 `/api/me`、`/api/profile?id=...` 的旧响应形状；不能本批强推未来 `/api/v1` 统一封装。

| 路由 | 领域方法与输入 | 输出/权限 |
| --- | --- | --- |
| GET `/api/user/profile` | `user_profile(actor_id)` | 当前用户资料 DTO，需登录 |
| POST `/api/user/profile` | `user_update_profile(actor_id, payload)` | 更新后的资料 DTO；仅自身，版本冲突409 |
| POST `/api/user/avatar/upload` | `user_upload_avatar(actor_id, content)` | `{upload_id, preview_url}`；登录、限体积，未选中前私有 |
| POST `/api/user/avatar` | `user_set_avatar(actor_id, upload_id, profile_version)` | 更新后的资料 DTO；`upload_id: null` 表示移除 |

头像上传 HTTP 输入采用现有项目 JSON 图片模式，字段为 `content`（Base64 字符串），无 angle、owner、path 等客户端字段。HTTP 层按解码后2 MiB及编码开销设置上限，严格解码，不能整个超大请求先读完才检查。A 负责 HTTP 解析，你负责二进制内容校验。

资料 DTO 是现有资料字段加上述新字段；私有自查也不返回手机号、密码散列、恢复码或收货地址，避免页面不需要却加载敏感数据。错误按现有 `{error: "可读说明"}` 和 HTTP 400/401/403/404/409 返回；不另创第二套错误封装。

旧 `AccountService.profile` 由 A 适配到 `user_profile`；旧 `update_profile` 由兼容适配实现上述旧字段规则。读取资料的新方法直接查用户表，不能调用旧 `profile` 形成相互递归。公开 `/api/profile?id=...` 继续返回 `{user, products}`，不把 `products` 包装改名。

如果发现现有路由/返回与此冲突，先在接入清单写明调整和影响，避免两个分支分别改接口。A 接线后你必须用真实 HTTP 和网页联调，领域测试通过不能代替。

## 6. U03：网页用户中心

1. 我的转角显示头像、昵称、学历层次、在读状态、简介；未填写有明确默认展示，不出现 `undefined`。
2. 资料表单使用选项，初始值与服务端一致；保存中禁用重复提交，成功提示；失败保留输入；409 引导核对最新值，不自动覆盖。
3. 公开主页展示公开资料和在售商品，隐藏手机号/地址；保留私聊、商品跳转和自己主页的特殊处理。信誉分明确不是交易担保，不能因点赞改分。
4. 保留订单、收藏、我发布的、信誉记录/申诉、退出、改密、管理员/客服工作台入口。不可为了“精简资料页面”把已有入口删掉。
5. 页面、头像 URL 和文本使用既有转义工具；事件进入独立 actions，表单 ID 取 `user-profile-form`，头像动作用 `user-avatar-*`。不重复注册原 `profile-form`。
6. API 请求复用 `core/http.js`；共享资料只写 `state.me`。退出/换账号后，旧请求完成不能写回新账号，复用既有会话保护思路；不要新建 `window.currentUser`。
7. 375/390/768/1440 宽度检查；键盘可操作、表单标签明确、头像替代文本合理，缩略头像失败时能回退。
