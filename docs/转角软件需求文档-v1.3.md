## 1. 产品定位与目标

转角是面向校园的二手交易与交流平台，帮助学生、毕业生出售闲置物品，让有需求的同学以较低成本购买，并通过平台订单、交付记录和售后渠道减少交易纠纷。

首批从广州华立学院广州校区的**计算机工程学院**试点，先覆盖少量专业、真实卖家和真实求购需求。商品以**逐本二手书、宿舍日用品、运动闲置、电子产品**为主，暂不以高价数码或奢侈品为核心。

产品希望完成三个基本结果：

1. 卖家能方便、如实地发布物品，买家能看清版本、缺陷、价格和交付方式。
2. 双方能在平台内沟通、出价、下单、约定交付，并在发生问题时留有可核查的记录。
3. 校园社区帮助同学交流、发布求购和认识其他卖家，但社区热度不作为交易信用担保。

### 1.1 已确定的经营约束

| 项目 | 要求 |
| --- | --- |
| 运营者 | 个人试做，当前没有公司主体 |
| 试做预算 | 人民币3,000元；不得将该预算理解为已经购买服务 |
| 首期地域 | 广州校区，优先计算机工程学院试点 |
| 注册资格 | 不要求学生证明或实名认证，毕业生可以使用 |
| 首期登录 | 手机号或邮箱＋密码；不发送短信，账号归属暂未验证 |
| 交易 | 模拟支付、模拟退款、模拟结算，不收取真实货款 |
| 客服时间 | 每天08:00—20:00，中国标准时间 |
| 品牌 | 统一使用"转角"；旧名称"华立转角"需要逐步替换 ❌ 尚未执行 |

### 1.2 试点成效

观察注册人数、真实有效商品数、求购响应、模拟下单完成率、取消原因、纠纷原因和客服处理时间。模拟成交量必须与未来真实成交量分开统计，不将测试数据当作平台业绩。

首轮建议邀请10—30名同学，完成至少5组买卖双方的完整试用，再决定是否扩大范围。这是试点建议，不是已完成的运营成果。

## 5. 账号、资料和隐私

### 5.1 注册与登录 ✅

1. 使用手机号或邮箱和密码注册，昵称必填；展示账号暂未验证的说明。
2. 不要求身份证、学生证、学号、学校邮箱或人脸材料。不将用户标为"实名""本校认证"。
3. 账号（手机号或邮箱）不可重复注册，邮箱按小写归一化；密码不得明文存储。当前试用规则为6—128字符。
4. 支持登录、退出、修改密码和安全恢复；连续错误尝试应限速或暂时锁定。
5. 无短信验证时，账号恢复需恢复码，不能仅输入手机号重置他人密码。
6. 改密或恢复后使旧会话失效。注册或登录失败应给出可理解的原因，避免无限转圈。

**实现要点**：密码使用加盐哈希；恢复码仅在生成时展示一次；登录失败 5 次锁定 15 分钟；改密或恢复后清除全部会话。

### 5.2 个人资料 ✅

### 7.6 下架与重新上架 ✅ V1.2 新增

> V1.1 第 16.2 节 A22 提到"重新上架"是针对**退货售后**的场景。本节描述的是**卖家主动下架**，两者的状态流转规则不同，不要混用。

**功能定位**：卖家挂上商品后，可能需要临时收起（自己还想留着、暂时不想卖、要改价重发）。下架不是删除，随时可以恢复。

**接口**

| 接口 | 方法 | 参数 | 说明 |
| --- | --- | --- | --- |
| `/api/my-products` | GET | `?status=removed` 可选 | 返回卖家自己的全部商品，**含已下架** |
| `/api/product/status` | POST | `{id, action:'delist'\|'relist'}` | 下架／重新上架 |

**状态流转规则**

| 当前状态 | 可下架 | 可重新上架 | 原因 |
| --- | --- | --- | --- |
| 在售 available | ✅ | — | 正常在售，可随时收起 |
| 已下架 removed | — | ✅ | 回到在售 |
| 已预留 reserved | ❌ | ❌ | **该商品已挂在某张待付款订单上**，下架会让那张订单指向一个消失的商品 |
| 已售出 sold | ❌ | ❌ | 交易已完成 |

**权限**：只有商品所属卖家可以操作自己的商品；他人操作返回 403。

**为什么不复用 `products()` 接口**：`products()` 会把 `removed` 的商品过滤掉（这是对的，买家不该看到），但卖家需要在"我发布的"里看到自己下架的东西，所以另开了 `my_products()`。

**界面**：`#listings` 路由（网页）／hub 页"我发布的"标签（小程序）。按状态分组展示，顶部有在售／已下架／已预留／已售出的数量统计。下架与上架按钮带二次确认。

### 7.7 下架与重新上架的门槛 🔧 本轮修复

7.6 的流转表只规定了「哪些状态能下架」，没有规定「**谁**能重新上架」。修复前存在两个洞：

| 洞 | 后果 | 修复 |
| --- | --- | --- |
| 置顶到期时间不随下架清理 | 一件商品付费置顶后下架，过段时间重新上架，**旧的置顶到期时间会被带回来**——若尚未到期则免费续了一次曝光 | 下架时一并把 `promoted_until` 清零；状态与置顶在**同一条 UPDATE** 中写入 |
| 重新上架不检查信誉与争议 | 因退款争议而信誉跌破 60 分的卖家，或刚发生退款的同一件商品，可以立刻重新上架继续售卖 | 重新上架前置校验：**信誉分 ≥ 60**，且该商品**未被任何退款／争议订单引用** |

**「退款锁定」（`refund_locked`）**：只要存在状态为 `refunded` 或 `disputed` 的订单引用了该商品，重新上架返回拦截提示。这与 10.6 的要求一致——**售后关闭不等于可以自动重新上架**，退货实物尚未回到卖家手中、或争议尚未结束时，该件实物不得重新进入流通。解除方式是按 10.6 的流程处理完争议，而不是重复点按钮。

### 7.8 商品下架后订单快照图仍须可看 🔧 本轮修复

**问题**：订单在创建时会把商品的标题、价格、图片地址存成**快照**（这是 7.1「已生成订单保存原信息快照」的要求，本身正确）。但图片本身是引用 `/media/<file_id>`，而该接口的放行条件是「该图仍被在售商品引用，或请求者就是上传者」。

商品一旦因退款、封禁或卖家下架变成 `removed`，条件的第一项不再成立；而订单里的商品图对买家来说，买家**不是上传者**，第二项也不成立 → 「我的订单」里商品缩略图变成 403 裂图。

**修复**：`/media/` 的放行条件补上第三种来源——**该图被任一订单的商品快照引用**：

```
允许读取 = 该图仍被非 removed 商品引用
        ∪ 该图被任一订单的 items 快照引用
        ∪ 请求者是该图上传者
```

私密图（`private` 标记）的规则不变，仍只有上传者与客服／管理员可读。

---

**未做**：下架后的商品不计入任何统计分母；管理员也看不到"某卖家下架了多少件"，这个运营视角尚未实现。

## 8. 沟通、出价、合并下单和交付

### 8.1 私聊与出价 ✅

用户已允许买卖双方私聊，可询问物品、缺陷和交付。**买家出价，卖家接受或拒绝**；接受后才可按约定金额进入订单。私聊口头承诺不能直接改变订单价格。

订单明确商品价、送货费及总价。模拟版平台服务费为 0；真实收费规则需另行公布并确认。禁止要求订单外补款。

### 8.2 合并规则 ✅

同一卖家的多件商品可合并下单、一次取货或一次送货，书仍逐本计价。不同卖家分开成单。

**同卖家合并送货时，取所选商品送货费中的最高值，只收一次**；自提不收送货费。该算法在订单提交前展示。

例：两本书分别10元、8元，各自送货费3元、5元；合并送货总价为10＋8＋5＝23元，而非26元。✅ 已按此实现。

### 8.3 交付约定 ✅

买家选择自提或送货，填写可用公共地点和日期时段；卖家确认。下单后24小时内需确认交付安排，这与"24小时内必须实际交货"不同。

订单保存商品、价格、费用、地点和时间快照。改约要由另一方确认；待确认改约不能覆盖原约定。✅

## 9. 订单、计时和模拟账务

### 9.1 主流程 ✅

浏览商品 → 私聊或出价（可跳过） → 确认商品与交付信息 → 创建订单并锁定商品 → 模拟付款 → 确认安排 → 实际交接记录 → 买家确认收货或满足自动收货条件 → 模拟结算 → 评价。

| 状态 | 用户可见含义 | 主要操作 |
| --- | --- | --- |
| 待付款 | 商品短暂锁定，尚未模拟付款 | 付款、**修改订单**、取消、超时关闭 |
| 已付款/待交付 | 模拟付款完成，等待安排或交付 | 确认安排、改约、符合规则的取消、售后 |
| 待买家确认交接 | 卖家已标记交付，买家尚未确认实际拿到 | 确认交接、确认收货、反馈未收到 |
| 待确认收货 | 买家确认实际交接，进入验收期 | 确认收货、售后、查看倒计时 |
| 已完成 | 已确认收货并完成模拟结算 | 评价、在规则期限内申请售后 |
| 已取消 | 未支付关闭，或取消并完成应有模拟退款 | 查看原因与记录 |
| 争议处理中 | 有有效售后争议 | 补充证据、协商、等待处理，暂停结算 |
| 已退款 | 模拟退款完成 | 查看处理结果和申诉入口 |

订单状态、交付状态、支付状态、退款状态、结算状态分别保存，界面可简化展示。⚠️ 当前界面仍以单一状态文本呈现。

### 9.2 三种计时必须区分 ✅

| 计时 | 现有试用默认 | 规则状态 |
| --- | --- | --- |
| 待付款有效期 | 创建后30分钟未付款，关闭并释放商品 | 试用默认，正式运营前可调整 |
| 确认交付安排 | 下单后24小时内确认；已付款未确认的超时订单取消并模拟退款 | 用户要求24小时确认 |
| 自动收货 | 买家确认实际交接后24小时，且无争议，才能自动完成和模拟结算 | 待最终确认 |

**不得从付款时间或卖家单方点击"已送达"开始无条件放款。**"确认实际拿到"与"确认商品验收完成"应分开。买家直接确认收货可以完成订单；买家报告未收到或发起争议时暂停自动结算。✅ 已按此实现。

超时任务在服务器执行，重启后仍能补处理；重复执行不得重复退款或结算。✅

**「确认交付安排」的 24 小时从何时起算（🔧 本轮修复）**

第二行的 24 小时窗口，起点必须是**买家完成付款的时刻**（`paid_at`），不是订单创建的时刻（`created`）。

修复前代码用的是 `created`。当买家把付款拖到接近 30 分钟超时边缘（例如第 29 分钟）时才付款，此时订单已创建近半小时，卖家的确认窗口被压缩；若买家付款时订单已创建超过 24 小时（例如通过改价重谈后续用同一张订单），`tick()` 会在买家付款后**立即**取消订单并退款——卖家刚收到款就被系统退款，与前端「付款后卖家 24 小时内确认交付时间」的文案直接矛盾。

修复后：`tick()` 取 `COALESCE(paid_at, created)` 作为起算点。`paid_at` 为空（不可能已付款却无时间戳）时兜底用 `created`，保证存量数据也能被处理。

> **回归测试**：`tests/test_defect_fixes.py::test_H4_confirmation_window_counts_from_paid_at` 构造「订单创建于 24 小时前、付款于 60 秒前」，断言 `tick()` 后订单**仍为 `paid`**、无退款分录。

### 9.3 取消、库存与并发 ✅ V1.2 修复

未付款可直接取消。已付款且未交付时按订单规则取消并退款；已发生交付后走售后。

**付款与取消同时发生、重复点击、多个买家争购时，结果必须一致，不能超卖或既退款又给卖家结算。**

> ⚠️ **本节曾存在实现缺陷，V1.2 已修复。** 详见 14.5。
>
> 修复前：三个线程并发抢同一件商品时，**偶尔会有两个买家同时下单成功**（真实重复售卖）。
> 修复后实测 20 轮，每轮都恰好 1 人成功。核对方式见 14.5。

### 9.4 账务记录 ✅

支付、退款、结算、结算冲回分别记账，金额采用整数分；每条记录关联订单、时间。✅

对账以服务端账务为依据（`/api/reconcile`），不能只看页面"成功"。✅

试用版所有相关页面和记录标明"模拟"，不得出现要求真实付款的二维码或转账指引。✅

### 9.5 付款前修改订单 ✅ V1.2 新增

**功能定位**：买家下单后、付款前，可能发现选错了交付方式、填错了地点、约错了时间，或者临时不想买其中一件。这时候双方都还没投入成本（买家没付钱、卖家没打包），改起来没有风险。

付款之后不适用本节，改时间要走原有的"申请改约"（需对方确认）。

**接口**

```
POST /api/order/update
{ id, product_ids?: [...], delivery?: 'pickup'|'delivery', address?: str, appointment?: ts }
```

**可改内容与权限**

| 字段 | 买家 | 卖家 | 说明 |
| --- | --- | --- | --- |
| `product_ids` 移除商品 | ✅ | ❌ | 传保留的商品 id 列表；未保留的会被移除 |
| `delivery` 交付方式 | ✅ | ❌ | 改成送货会重算送货费 |
| `address` 收货地点 | ✅ | ❌ | 送货时必填；自提时自动清空 |
| `appointment` 交付时间 | ✅ | ✅ | 双方都可改，须在 60 秒后至 30 天内 |

**状态前置条件**：仅 `awaiting_payment`。已付款调用返回 400，提示改用"申请改约"。

**移除商品的连带处理**（这是本节最容易出错的地方）

1. 被移除的商品从订单 `items` 中删除
2. 该商品状态从 `reserved` 释放回 `available`，重新出现在公开列表里
3. 重算 `subtotal`（剩余商品价格之和）
4. 重算 `delivery_fee`（若为送货，取剩余商品送货费的最高值；若为自提则为 0）
5. 重算 `total = subtotal + delivery_fee`
6. 在 `order_notes` 表记录"买家移除商品：XXX"，供事后追溯

**边界校验**

- 订单至少要保留一件商品，全部移除返回 400
- 传入的 `product_ids` 必须都属于本订单，否则返回 400
- 改成交付方式后，订单内所有商品都必须支持该方式，否则返回 400
- 非订单当事人调用返回 403

**界面**：订单卡片上"修改订单"按钮（仅待付款状态显示，买卖双方都可见）。弹窗内可勾选/取消勾选商品，选择交付方式、填写地点、选择时间。取消勾选的商品在弹窗里会变灰，保存前就能看出会移除哪些。

**小程序**：原生端用 `wx.showActionSheet` + `wx.showModal` 走"交付方式 → 地点 → 时间"三步。⚠️ **小程序端不支持移除订单内商品**（原生弹窗难以承载勾选列表），需要该操作请用网页端。

### 9.6 卖家取消订单 ✅ V1.2 新增

V1.1 原文只允许买家取消。V1.2 放开给卖家，但**仅限买家付款前**：

| 调用者 | 订单状态 | 是否允许 |
| --- | --- | --- |
| 买家 | 待付款 / 已付款 | ✅ |
| 卖家 | **待付款** | ✅ V1.2 新增 |
| 卖家 | 已付款及以后 | ❌ 提示走客服流程退款 |

理由：卖家在买家付款前取消不涉及资金；付款后由卖家单方取消会产生退款责任，应走客服流程留痕。

> **⚠️ V1.3 对「买家 已付款 ✅」一行的定性说明。**
> 缺陷审计初稿曾把「买家在已付款状态可自助取消并自动全额退款」列为缺陷，理由是该路径绕过了客服判定、对接单卖家不公平。
> 复核后确认：**这是 V1.2 已明确记录并确认的设计**，实现与需求一致，不构成缺陷，因此本轮**没有修改这一行为**。
> 但该设计的公平性确有讨论空间——它意味着卖家一旦接单就不再享有单方退出的对称权利，而买家保留。此点已转入 17 节「待决产品规则」，由产品决策而非缺陷修复处理。

### 9.7 求购撮合成交后的回滚 🔧 本轮修复（新增章节）

**功能背景**：社区里有人发求购（`wants`）。卖家看到后可以点「我要这个」把自己的商品挂到这条求购上，买家从求购进购物车结算，订单会带上关联的求购编号。成交时系统做两件事：把求购状态置为 `matched`（已成交），并按小计收取 5% 的**撮合服务费**记账到 `ledger`。

**问题**：`orders` 表**没有存 `want_id`**。订单与求购之间没有可回溯的关联，于是三条本该回滚的路径全部失灵：

| 路径 | 修复前的结果 |
| --- | --- |
| 买家取消订单 | 订单变 `cancelled`、商品释放回 `available`，但**求购永久停在 `matched`**、服务费**仍挂在账本上** |
| `tick()` 超时取消 | 同上 |
| 退款（客服结案） | 同上 |

用户侧的直接表现是：求购页永久显示「已成交」，且「查看匹配」按钮消失（前端只在 `status==='open'` 时渲染该按钮），发帖人再也无法为这条求购找到卖家——**这条求购等于被永久作废了**。同时账本上凭空多出一笔从未真实发生的服务费。

**修复内容**

1. `orders` 表新增 `want_id INTEGER`（NULL 表示普通下单）。老库通过 `PRAGMA table_info` 探测后自动 `ALTER TABLE` 补列。
2. 新增回滚助手 `restore_want(c, r)`：把求购从 `matched` 恢复为 `open`，并写入一条**反向分录**冲销服务费。
3. 接入三条路径：`cancel` 动作、`tick()` 的两个超时分支、`support` 的退款流程。
4. **改单同样重算**：`update_order` 移除商品后小计变小，服务费按 `subtotal * 5 // 100` 重新计算，避免服务费始终按原始小计收取。

**账本科目**：`ledger` 上有 `UNIQUE(order_id, kind)` 约束，同一订单同一科目只能有一条记录，所以冲销不能复用 `service_fee`，新增了独立科目：

| 科目 | 含义 |
| --- | --- |
| `service_fee` | 撮合成交时按小计 5% 收取 |
| `service_fee_reversal` | 成交回滚时的冲销（金额与 `service_fee` 相等、方向相反） |

前端「我的订单」的账本明细已同步补上这两个科目的中文标签：「撮合服务费」「服务费冲回」。

**前端关联状态的修复**：`state.pendingWant` 原本只存一个求购编号、且只在结算成功的回调里清空。用户点了「我要这个」之后中途改主意（清空购物车、或直接去逛别的商品），这份关联仍留在内存里，**下一笔完全无关的订单会带上 `want_id`**——那条求购被错标为已成交，还多记一笔 5% 服务费。

现在改为：`pendingWant` 存 `{want, product}`，并在三处自动失效——购物车内容变化时同步校验（`syncPendingWant`）、购物车加载时重置、结算页提供「清除关联」按钮（`clear-want`）。购物车页在有未结算的求购关联时显示提示条，明示「本次结算将关联求购 #N」，把隐式关联变成用户可见、可取消的状态。

> **回归测试**：`test_H2_cancel_restores_want_and_reverses_fee`（取消后求购回到 `open`、账本出现冲销分录）、`test_H2_timeout_restores_want`、`test_H2_refund_restores_want`、`test_H2_edit_order_recomputes_service_fee`。
>
> ⚠️ 本节的**后端**部分（`want_id`、`restore_want`、服务费重算）有自动化测试覆盖；**前端** `pendingWant` 的三处失效逻辑属于浏览器内存状态，**没有自动化测试**，只能靠浏览器冒烟脚本的实际交互验证。

### 9.8 订单与售后通知 🔧 本轮新增（新增章节）

**问题**：前端文案里已经有「订单通知」「查看订单通知」，但后端**没有任何订单事件流**——`messages` 表只服务聊天。买家下单、付款、改约、售后，卖家侧收不到任何提醒，只能自己反复刷新订单页。

**实现**：新增独立的通知表与接口，与聊天消息完全分离。

```
notifications(
  id, user_id, kind, order_id, ticket_id, body, read_at, created
)

GET  /api/notifications           → {unread, items}
POST /api/notifications {id}      → 标记单条已读；不传 id 则全部标记已读
```

**触发点**（写入通知的事件）

| 事件 | `kind` | 通知对象 |
| --- | --- | --- |
| 买家下单 | `order_created` | 卖家 |
| 买家付款 | `order_paid` | 卖家 |
| 卖家标记交付 | `order_delivered` | 买家 |
| 买家确认交接 | `order_handover` | 卖家 |
| 订单取消 | `order_cancelled` | 对方 |
| 订单完成结算 | `order_completed` | 卖家 |
| 申请改约 | `order_reschedule` | 对方 |
| 改约被接受／拒绝 | `order_change_result` | 发起方 |
| 订单在付款前被修改 | `order_updated` | 卖家 |
| 提交工单 | `ticket_filed` / `ticket_refund` | 对方 |
| 工单回复 | `ticket_reply` | 相关用户（**内部备注不通知**） |

**界面**：消息页左侧会话列表**置顶**一个「订单与售后通知」入口（铃铛图标 + 未读数），点进去是独立面板：未读项高亮，「全部标记已读」按钮在有未读时才出现。它复用消息页的路由（`#messages/notice`），但**不是聊天会话**——不参与轮询、没有输入框。

**范围说明**：本轮做的是**站内通知**，这是 10.5 认定的首期必需能力。浏览器后台推送、微信订阅消息、短信、邮件各自需要授权与接入，**均未实现**；不能承诺窗口关闭后仍能提醒。客服工作台一侧的通知（分栏、未读数、声音提示）仍未做，见 10.5。

## 10. 售后、客服和纠纷处理

### 10.1 受理范围 ✅

支持未收到、未按约定交付、版本不符、未说明缺陷、物品与描述不符、协商退货及其他反馈。

不承诺平台无条件包赔或所有二手物品无理由退货，也不写成"二手商品一律不能退款"。是否退款结合描述、约定、交付、证据和适用规则判断。

### 10.2 工单流程 ✅

选择订单/举报对象 → 选择原因 → 填写诉求并提交图文证据 → 双方回复和协商 → 客服处理 → 退款等结果执行 → 关闭或申诉复核。

工单状态包含待处理、处理中、待复核、已解决。支持处理理由、时间线、相关订单、内部备注及用户可见回复。✅

处理结果可包括不退款、仅退款、退货退款、双方认可的部分退款。退款金额不得超过可退金额。✅

### 10.3 客服工作台 ✅

显示每日08:00—20:00的服务时间；非工作时间仍可提交。⚠️ 是否真人在线须按实际值守显示，当前未做在线状态标识。

工作台支持按状态筛选，认领、回复、记录依据、提交处理结果。客服不得处理自己的买卖或相关利益冲突工单。✅ 单人工单已有角色校验。

### 10.4 客服账号与权限 ⚠️

当前试用版有工作台和 support/admin 角色判断，但没有供所有人共用的默认客服号码或密码。现有本地管理命令可由项目操作者建立**管理员账号**：

```powershell
cd "E:\zi\huali-corner-trial\Backend mission"
python manage_trial.py create-admin
```

应在正在使用的项目目录和同一试用数据目录执行，并使用独立管理号码。✅

❌ **「人员与权限」界面未做**：平台管理员为每位客服单独建立或受控授权账号、停用离职账号、撤销会话并留审计记录。当前只能靠命令行建号。

**推荐权限分工（待实施）**：客服受理、认领、协商、核验证据并提出处理建议；平台管理员批准退款及信誉处罚；涉及本人交易时必须交给无利益冲突的授权人员。

### 12.4 封禁账号的在途订单与商品处置 🔧 本轮修复（新增章节）

封禁（`ban_user`）不只是一次状态写入——被封的账号可能同时是若干张订单的买家或卖家，这些在途订单必须一并处置，否则会卡在中间状态无人推进。

**修复前的问题**

| 场景 | 修复前的后果 |
| --- | --- |
| 封禁卖家 | 只把 `status='available'` 的商品下架。**`reserved` 商品（正挂在待付款订单上）未处理**；已付款、已交付的订单仍停在 `paid` / `awaiting_handover`，而卖家已无法登录推进，买家只能自己发现异常再去发售后，或干等 `tick()` 的 24 小时兜底 |
| 封禁买家 | 他名下已付款的订单无人退款，卖家不敢交付又无法取消 |
| 解封 | 未校验目标当前状态，对未被封禁的账号也能执行「解封」，白写一条操作记录 |

**修复后：封禁时自动清算在途订单**（`_settle_banned_orders`）

| 订单角色 | 订单状态 | 处置 |
| --- | --- | --- |
| 被封者作为**买家** | `awaiting_payment` | 取消订单，商品释放回在售 |
| 被封者作为**买家** | `paid` / `awaiting_handover` | 取消并**模拟退款**给买家 |
| 被封者作为**卖家** | `awaiting_payment` | 取消订单，商品释放回在售 |
| 被封者作为**卖家** | `paid` / `awaiting_handover` / `awaiting_receipt` | 订单转 `disputed`，并**自动为买家开一张退款工单**（所有权归买家），进入客服队列 |

所有取消路径同时调用 9.7 的 `restore_want`，求购关联一并回滚。

**解封的前置校验**：只有 `status=='banned'` 的账号可以解封，否则返回「该账号当前不是封禁状态，无法解封」。

> ⚠️ **仍未做的部分**：封禁时不会**自动**扣信誉分或**自动**批准退款——转 `disputed` 的订单仍需客服按 10.2 的流程核定，这是有意的，避免「一封禁就等于认定退款」。被封者若有尚未交付完的订单，其申诉入口按 12.3 保留（可查看记录、可申诉）。

### 14.5 数据库并发写入规则 ✅ V1.2 修复（新增章节）

> 本节记录一个**已修复的真实缺陷**与随之确立的实现约束。改动 `Backend mission/db.py` 前必读。

**修复前的缺陷**

| 现象 | 影响 |
| --- | --- |
| 并发写入时随机抛 `sqlite3.OperationalError: attempt to write a readonly database` | 30 并发写约 2–5 次失败，接口返回 500 |

根因：本项目写法是"每次事务新开连接、用完即关"，而 SQLite 的 WAL 模式下**最后一个连接关闭时会自动 checkpoint 并删除 `-wal` / `-shm` 文件**。此刻另一个线程刚开好连接准备写入，找不到 wal 文件即报"只读数据库"。

**修复**

不使用 WAL，改用默认的删除日志模式：在 `app/core/database.py` 初始化时执行一次 `PRAGMA journal_mode=DELETE`，同时把旧库迁出 WAL。该 pragma 绝不能放进 `connect()` 每次连接都执行 —— 它需要短暂的独占锁，多线程同时执行会互相冲突。

**两处曾被写错、现已更正的说法**

1. **没有发现真实超卖。** 早期一次并发测试里出现"两人下单成功"，排查后确认是测试用例复用了
   **同一个幂等 key**，两个线程拿到的是同一张订单 —— 这恰恰是幂等设计想要的结果，
   并不是一件商品卖给了两个人。改用各自独立的 key 重测：3 线程抢同一件商品，
   加不加写锁都是 0 次超卖。真正挡住超卖的是 `checkout` 事务内的库存状态校验，不是下面那把锁。
2. **写锁不是这次修复的关键。** 切到 DELETE 日志模式之后，30 并发写 × 5 轮，
   加锁与不加锁都是 0 失败 —— 真正解决问题的是换日志模式。
   `app/core/database.py` 里的 `_WRITE = threading.RLock()` 仍然保留，
   作用是让写事务串行、避免多线程交叉持有 `BEGIN IMMEDIATE`；
   但**不要把它当成并发安全的保证**：它只在单进程内有效，多进程部署或将来的真实数据库都不成立，
   库存正确性仍要靠事务内的状态校验。

**验证结果**

| 场景 | 结果 |
| --- | --- |
| 30 线程并发写 × 5 轮 | 0 / 150 失败 |
| 3 线程并发抢同一商品（各自独立幂等 key）× 20 轮 | 20/20 轮恰好 1 人成功，0 次超卖 |
| 20 线程并发读 | 0 失败 |

对应测试：`tests/test_market.py::test_concurrent_checkout_one_winner`
（改为按数据库中的订单条数与不同订单号计数来断言，不再被幂等返回干扰）、
`tests/test_market.py::test_concurrent_checkout_distinct_keys_no_oversell`。

### 14.6 认证类数据的定期清理 🔧 本轮修复（新增章节）

`sessions`（登录会话）、`otp`（验证码）、`auth_attempts`（登录失败限速计数）三张表此前**没有任何清理机制**——只在用户下次登录时覆盖自己那一行。结果是：

- 已过期但未再登录的会话行永久残留；
- 无人再用的手机号对应的验证码行永久残留；
- 限速计数窗口结束后不再被读取，但记录仍占表。

**修复**：把清理挂进已有的后台 `tick()` 任务（该任务本身负责超时订单，重启后仍会补跑），每次执行顺带清掉：

| 表 | 清理条件 |
| --- | --- |
| `sessions` | `expires < now` |
| `otp` | `expires < now - 86400`（多留一天，便于排查用户反馈的登录问题） |
| `auth_attempts` | `reset_at < now - 86400` |

用「过期后再宽限一天」而不是立即删除，是为了在用户报告「验证码/登录异常」时还能查到痕迹。

### 14.7 前端随机标识的兼容性 🔧 本轮修复（新增章节）

结算下单与发送消息都需要生成一个**幂等键**（`request_key`），用于「网络超时后重试不会重复下单／重复发消息」。前端原本直接用 `crypto.randomUUID()`。

**问题**：`crypto.randomUUID` **只在安全上下文存在**——即 `https:` 或 `localhost` / `127.0.0.1`。而试用版 `start-trial-8081.bat` 极可能被同学用**局域网 IP**（`http://192.168.x.x:8081`）访问，这是普通的非安全上下文，`crypto.randomUUID` 为 `undefined`，结算与发消息会直接抛 `TypeError`，用户看到的是「点了没反应」。

**修复**：`core/dom.js` 新增统一的 `uid()`：

1. 若 `crypto.randomUUID` 可用 → 直接使用；
2. 否则用 `crypto.getRandomValues`（该方法在非安全上下文**可用**）取 16 字节，手工置版本位与变体位，拼成标准 UUID v4 字符串。

两处调用点（结算、发消息）统一改走 `uid()`。产物仍是合法 UUID，幂等键的语义不变。

> **回归验证**：冒烟脚本在页面内临时抹掉 `crypto.randomUUID` 后调用 `uid()`，产物通过 UUID v4 正则校验。

### 19.5 定性修正：一条审计结论被推翻

审计初稿把「买家可在已付款、未交付时单方取消并自动全额退款」列为中危缺陷（M3），理由是它绕过了客服判定、对接单卖家不公平。

**复核结论：这不是缺陷。** 需求文档 9.6 的权限表已明确记录「买家 | 待付款／已付款 | ✅ 允许取消」，实现与该记录一致。审计时的判断错在把后端给**卖家**的提示文案（「已付款的请走客服流程退款」）误当成了对买家的约束。

本轮因此**没有修改该行为**。但该设计的公平性确有讨论空间——卖家一旦接单即丧失单方退出的对称权利。此点已转入 17 节「待决产品规则」，由产品决策处理，而不是当成实现缺陷悄悄改掉。

> 记录这一条的目的：审计报告本身也会有判断失误，把「实现偏离需求」与「需求本身值得商榷」分开，才能避免用修 bug 的方式改产品政策。

### 19.9 补记：账号支持邮箱（同日追加）

**需求来源**：运营者需要一个好记的调试管理员账号，希望用邮箱而不是手机号。

**变更**：账号标识从「11 位手机号」放宽为「**11 位手机号或邮箱**」。

| 环节 | 变更内容 |
| --- | --- |
| 后端校验 | `_phone()` 增加邮箱分支；邮箱统一转小写后存储与比对，`904429801@QQ.COM` 与 `904429801@qq.com` 视为同一账号 |
| 网页登录框 | 账号输入由 `type="tel"` 改为 `text`，去掉 `pattern="1[3-9][0-9]{9}"`，改为「必填 + 最长 120 字符」——格式规则统一交后端判定，避免前后端两套正则跑偏 |
| 小程序 | 同步去掉 `type="number" maxlength="11"` |
| 提示文案 | 「请输入11位手机号」→「请输入11位手机号或邮箱」；「手机号、密码或恢复码不正确」→「账号、密码或恢复码不正确」；注册冲突提示同步改为「此账号已注册」 |
| 客服工作台 | `mask_phone()` 增加邮箱脱敏，保留用户名前 2 位与完整域名（`90***@qq.com`）——域名本身不指向个人，保留它才能判断是否校内邮箱 |
| 管理命令 | `manage_trial.py` 账号输入改为「手机号或邮箱」；同时修正 `reset-password` 分支**未接收 `_phone()` 规范化返回值**的问题（否则大写邮箱会查不到账号） |

**明确不变的部分**

- 短信验证码（`request_code`）**仍只接受手机号**——邮箱收不到短信，这一条不受影响。
- 请求字段名沿用 `phone`，不改动既有前端与数据表结构；语义已是「账号标识」。
- 账号仍未经验证：不发送短信、不做实名或学籍认证，页面上的说明文字同步从「手机号未验证」改为「账号未验证」。
