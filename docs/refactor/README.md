## 本次架构决策

1. 实施起点使用当前 `b2b6266` 及后续经核实的新提交。历史重构分支作为代码参考，逐项移植，不整体替换当前版本。
2. 以一个 Python 业务系统承载全部领域；模块通过显式依赖协作。路由只处理协议，服务组织用例，纯规则独立测试，D1 适配负责 SQL 与原子提交。
3. 本地默认使用隔离的 Wrangler D1/R2 环境验证目标实现。旧 SQLite/MySQL 运行路径在过渡期保留，停止为其复制新增业务逻辑；它们是否仍是实际数据源必须在迁移盘点确认。
4. Vue 按业务模块组织，采用共享布局、基础组件、API 契约和设计令牌；Pinia 只承载跨页面状态。保留紫色 ZJ 标识、暖黄操作色、紧凑双专题和现有五槽手机导航。
5. 先维护行为合同，再替换实现。缺陷修复、业务改规则、新增功能与纯结构迁移分别登记；接口和数据结构变更必须有兼容方案。
6. 不引入微服务、Redis、消息中间件或全套复杂领域框架。聊天先完善轮询；是否需要实时连接由后续实际数据决定。

## 设计如何约束后续新增功能

每个新增功能须写明：所属领域、API/数据变化、权限与归属、事务和幂等、页面入口、复用组件、六类页面状态、测试与迁移方式。实现者按 03 的开发规范编码、按 04 的界面标准验收、按 05 的任务格式提交证据。

规范先随本次设计进入仓库，工具配置和 CI 在实施任务中落地。不能声称现在已经存在 ESLint、Ruff、Vue、OpenAPI 或视觉回归流水线；也不因历史文件尚未达标而全仓格式化。

## 文档依据与适用边界

- 用户提供的 [架构分析提示词](../../../华立转角-GPT6-Astra架构分析与重构提示词.md) 是本次分析的输入；本次采用其中与用户请求一致的分析、设计和保留数据要求。文档内描述的部署、业务或历史状态仍须核对源码和证据。
- 既有 `docs/superpowers/specs/2026-10-21-backend-decoupling-design.md` 是较早的“仅后端解耦、保留框架”方案。本计划根据最新的全项目重构请求，扩展为 Vue/FastAPI 目标；其显式依赖、事务边界和渐进交接原则继续采用。
- `docs/standards/转角软件开发规范-v1.0-审阅草案.docx` 与旧协作文档保留为历史来源。本次对技术栈、四级角色、分支和规范生效阶段作了更新，不能拿旧的“不要迁移框架”或“三个角色”覆盖用户的新要求。
- 代码已核实；本轮不把发布说明中的线上测试、部署版本或数据库备份当作本轮亲自验证。没有连接真实 D1/R2，没有部署、切流量或启用收费资源。
