# 转角后端解耦重构设计

日期：2026-10-21。状态：待用户审阅的设计，尚未修改业务源码或部署。

## 1 目标与范围

本次目标是降低模块之间的耦合，让后续增加功能时能明确知道需要修改哪个模块、依赖哪些接口、运行哪些测试。具体改善命名、可读性、重复逻辑、隐式依赖和维护成本。仅整理目录或拆出更多 mixin，不能算完成解耦。

默认约束：保留现有 HTTP 路由、入参、返回字段、错误状态、权限、订单状态机、金额整数分、会话政策及存量数据库结构。发现业务缺陷时单独记录和处理，不把行为变更混进结构重构。保持本地 Python 与 Cloudflare 双运行时，不迁移框架，不增加新的运行时依赖。

先做后端。前端仅在后续验收时核查兼容性，不顺带改界面。真实账号、订单、商品、图片、聊天、工单和数据目录保持安全。代码同步不等于将本地数据库覆盖到 D1。

## 3 主要耦合点

### 3.1 多继承隐藏跨模块依赖

`app/market.py` 将 Store 和各领域 service 混入同一实例。业务代码可以直接调用任意 `self.*`，没有构造参数或显式接口说明依赖。测试通常也必须创建完整 Market。

示例：TradeService 调用社区的 `_close_support` 和 `chat_unread`；SupportService 调用交易的 `journal`、`release`、`restore_want`、`order`；CommunityService 依赖交易模块中的 `notify`。文件拆开了，运行时职责仍交织。

### 3.2 职责集中

- `app/community/service.py`：734 行，43 个函数，混合聊天室、客服会话、好友、论坛、求购和内容处置。
- `app/support/service.py`：438 行，既有工单、信誉、封禁、档案，也有交易评价。
- `app/trade/service.py`：281 行，混合订单、账本、站内通知、角标和跨业务定时任务。
- `server.py`：438 行，其中 `handle_request` 为 229 行，集中做路由分发和请求处理。
- `app/cloudflare/api.py`：593 行，承担装配、部分路由和账号、商品等实现。
- `app/core/database.py`：447 行，混合连接、方言改写、schema、迁移和事务。

以上行数是本轮只读检查的快照，不将第三方 Pillow 或内置词库的大文件算作业务重构目标。

### 3.3 双运行时的业务重复

本地 service 与 Cloudflare adapter 各有业务实现。直接将同步数据库 API 套到异步 D1 会破坏原子性，不能靠一个通用数据库抽象强行合并。

## 4 方案比较

1. **推荐：渐进式组合服务。** 保留 Market 和现有路由作为兼容入口，逐个将领域能力改为通过构造参数注入的独立对象。每批可测试、可回滚，后续逐步去掉跨 mixin 调用。代价是短期保留兼容转发层。
2. **仅继续拆文件和 mixin。** 改动少，适合临时整理，但 `self.*` 隐式依赖继续存在，不能充分满足解耦目的。
3. **整体更换框架和数据访问层。** 改动面大，双运行时和存量数据兼容验证成本高，不适合作为本次起点。

采用方案 1。先建立一个真正独立、可测试的通知边界，再按同一模式迁移其他领域，不一次性重写后端。

## 5 目标依赖方向

HTTP 适配层负责解析、认证和错误响应，调用应用服务。应用服务编排领域规则与事务。领域规则不导入 HTTP、Worker bindings 或完整 Market。数据访问与平台适配通过明确接口供服务使用。组合根负责构建对象，其他模块不反向引用组合根。

本地 SQLite/MySQL 和云端 D1 各自保留事务实现；复用可证明语义一致的纯校验、状态判断和常量。复用前先检查两端是否存在刻意的权限或环境差异。

所有写入同一业务事务的数据必须使用调用方传入的同一个事务上下文。存储适配不私自提交，不在业务写入中另外打开连接。D1 多语句写入继续使用已有 `batch` / `guarded_batch`；不把它当支持交互式多次 await 的 SQLite 事务。

## 6 第一批实施边界

### 6.1 独立通知模块

新增 `app/notifications/service.py` 与 `repository.py`。NotificationService 通过构造参数接收通知仓储和时钟；通知仓储通过构造参数接收明确的查询能力。它不继承 Store、TradeService、CommunityService，也不依赖 Market。

建议能力：在指定事务中写入通知、读取用户通知列表、计算未读数、标记一条或全部已读。保留当前分页和参数语义，不把校验或分页策略变化夹带进重构。

写入方法明确接收 `transaction`，继续由调用方控制提交与回滚。已读操作的事务由应用入口创建并交给服务，避免仓储自己提交。

Market 初始化并持有独立服务，现有 `notify`、`notifications`、`read_notifications` 方法仅作兼容转发，保持旧参数顺序、返回值和同步调用方式。交易、论坛、客服的旧调用可以先继续经过这些转发方法，不要求在同一批修改所有模块。

### 6.2 角标编排

`badges` 继续属于应用聚合入口：分别获取通知未读数与聊天未读数。不能把聊天查询塞入 NotificationService，也不能反向导入 CommunityService。

### 6.3 双运行时的边界

第一批先解除本地通知与交易类的所有权耦合，Cloudflare 现有接口保持。记录两端通知合同，并运行两端现有相关测试。第一批不能宣称已消除所有双运行时重复；云端异步仓储在后续批次实现，不让同步仓储访问 D1。

### 6.4 第一批明确不包括

不改账本算法、退款规则、通知类型和文案、订单状态、客服超时规则、认证算法、会话时长、数据库 schema 或 HTTP 地址。暂不拆交易状态机和巨型路由，避免首批同时改动多个高风险边界。

## 7 后续批次

1. **交易与定时编排。** 区分订单用例、账本记录、库存恢复和定时任务；把客服超时交还客服服务，由调度入口编排。订单、库存、账本和通知仍必须在同一原子边界内，不能各服务独立提交。
2. **社区与客服。** 按论坛、好友、聊天、客服会话、求购建立明确服务；交易评价从工单服务分离。只有出现实际重复或跨模块使用时才抽取公共规则，避免通用工具大杂烩。
3. **HTTP 路由。** 按领域建立处理器，统一参数和异常边界；保留端点和状态码，Cloudflare 与本地都跑接口合同测试。路由层不直接拼业务 SQL。
4. **数据层。** 分离连接与方言、建表与增量迁移，逐步将 SQL 放回有职责的仓储。数据库变化另做数据副本验证，不能用重构为由直接修改真实库。
5. **重复规则与规范。** 核对状态、时间间隔、金额规则，再提取带单位和业务含义的常量，清理密集单行和模糊命名。仅对本批触及代码整理，避免全库格式化造成大面积 diff。

每批独立说明解决了什么依赖、保留了什么耦合、运行了什么测试；通过后才扩展到下一批。
