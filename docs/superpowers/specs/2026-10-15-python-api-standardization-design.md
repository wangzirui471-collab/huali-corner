## 1. 目标和范围

用户要求利用适合的GitHub基础能力完善转角，并统一Python数据处理、接口返回、字段命名和代码风格。本次不是另起一个不兼容的演示系统，也不能用规范重构宣称全部业务需求完成。

Python统一负责数据校验、访问权限、存储、交易计算、账务、状态变化和对外序列化。网页与小程序保留必要的界面代码，只提交操作和用户输入、展示后端确认的结果；前端单位换算不能成为最终价格或付款状态的依据。

交易、社区、客服继续保留在试点范围内；缺少的业务流程见[需求实现核对表](../../需求实现核对表-2026-10-15.md)。本设计先统一这些既有模块的合同，不把全部功能补齐或真实支付上线夹进一次接口重构。

现有数据必须保留；不得重建账号、删除数据库、移除交易校验、关闭安全响应头，或用共享账号替代独立登录。新品牌统一为转角，仍明确模拟交易和未验证手机号。

## 3. Python模块边界

建议在现有仓库中逐步组织以下职责，具体文件拆分在实施计划中确定：

- API入口与路由：负责HTTP、身份上下文、请求模型、调用业务与返回响应。
- contracts：请求、公开响应、分页、错误和枚举模型；数据库行不是API合同。
- services：账号、商品、订单、售后、社区、信誉、账务；保留已有核心规则并逐步改善命名。
- repositories：参数化SQL、事务、查询与受控迁移；不决定某个公开接口可见哪些字段。
- core：配置、时钟、日志、错误、权限与常量。
- legacy：必要的旧API适配；新字段与旧字段的映射只能集中在边界层。

同一笔业务只允许一份权威实现。旧接口和v1接口共享交易服务，不复制退款、收货计时或密码校验逻辑。保留现有密码摘要和恢复码机制，不在本次顺带更换密码算法或会话方案。

## 4. 统一HTTP返回格式

新接口前缀为 `/api/v1`，UTF-8 JSON。每个JSON响应均有相同的七个顶层字段：

```json
{
  "code": "OK",
  "message": "成功",
  "data": {
    "id": 12,
    "price_cents": 1500,
    "created_at": "2026-10-15T08:00:00Z"
  },
  "errors": [],
  "request_id": "a73bc079998b450f9697796b881fc1d6e",
  "api_version": "v1",
  "transaction_mode": "simulation"
}
```

- code：稳定的英文业务码，成功固定OK，程序不依赖中文message分支。
- message：面向用户的中文提示，不包含异常堆栈或秘密。
- data：成功业务数据；无返回内容的操作为null；失败为null。
- errors：字段问题数组，无字段错误为空数组；条目只包含field、code、message。
- request_id：服务器生成的关联标识，同时放入X-Request-ID响应头；客户端不能用任意字符串污染日志。
- api_version：固定v1；与URL前缀一致。
- transaction_mode：当前固定simulation；不得用此标记伪装真实支付。

失败示例：HTTP422，code为VALIDATION_ERROR，data为null，errors为 `[{"field":"price_cents","code":"INTEGER_REQUIRED","message":"价格必须以整数分提交"}]`，其余字段保持存在。

HTTP状态码保留语义：200读取或操作成功，201新建成功，400非法JSON，401未登录，403无权限，404不存在，405方法不支持，409状态/幂等冲突，413请求过大，415不支持的媒体类型，422字段校验，429限速，500未预期异常。不是所有情况都返回200。

统一处理业务错误、框架404/405、请求与响应模型校验、限速和未预期异常，防止出现框架原始detail返回。校验输出必须剔除Pydantic原始input与敏感上下文，尤其不能回显密码、令牌或恢复码。500只向用户提供通用提示，通过request_id定位内部日志。

图片、静态文件和未来下载文件保持相应二进制类型，不套JSON成功包络；API鉴权失败仍按错误模型返回。健康检查提供v1包络；托管平台旧探针在兼容期继续可用并单独记录。

## 5. 命名和基础类型

| 对象 | 统一规则 |
| --- | --- |
| Python文件、函数、变量、JSON字段和数据库新字段 | snake_case英文名称；不混用拼音、缩写和驼峰 |
| Python类、请求和响应模型 | PascalCase，例如ProductCreateRequest、ProductResponse |
| 常量和错误码 | UPPER_SNAKE_CASE；常量和枚举集中定义 |
| 资源自身标识 | id；现有用户/订单等整数ID保持整数，媒体ID保持原有随机字符串 |
| 关联标识 | user_id、seller_id、buyer_id、product_id、order_id、room_id、ticket_id |
| 金额 | 非负整数分，以_cents结尾；拒绝浮点数、负数和JSON布尔值 |
| 时刻 | UTC的ISO8601字符串，以_at结尾，空值为null；前端按Asia/Shanghai显示 |
| 自然日期 | purchase_date使用YYYY-MM-DD或YYYY-MM，配合purchase_date_precision为day/month/unknown；未知时null |
| 布尔值 | is_或has_前缀；严格接受JSON true/false，不使用bool('false') |
| 数量与积分 | like_count、member_count、credit_score、score_delta等带明确语义 |
| 无值 | 模型允许时用null；空列表用[]，禁止以0、空串或字符串null混充缺失 |

保留当前资源ID类型，避免重写订单关联；整数标识限制在前端安全整数范围内。对外时间标准化不要求立即把数据库中原有秒级数值改成字符串；Python序列化层负责转换，解析时拒绝无时区的时刻。

已有数据库字段先由repository和序列化模型映射。需要物理改表时使用有版本、可备份和可回滚的迁移，禁止全局搜索替换JSON内容、SQL列名和用户文本。

## 6. 重点字段映射

| 当前字段或语义 | 新API字段 | 适用说明 |
| --- | --- | --- |
| price | price_cents | 商品标价 |
| original_price | original_price_cents | 原购买价格，可未知 |
| delivery_fee | delivery_fee_cents | 送货费 |
| subtotal、total | subtotal_cents、total_cents | 订单小计和总额 |
| amount | amount_cents | 报价或账务金额；语义由所属模型确定 |
| created | created_at | 创建时刻 |
| appointment | appointment_at | 当前单个约定时刻；完整时段需求后续扩展 |
| paid_at、handover_at、completed_at | 保持名称，统一序列化格式 | 不再混用数字秒和时间字符串 |
| key、request_key | idempotency_key | 下单和发送消息；同资源范围及用户内校验 |
| peer、target | peer_user_id、target_user_id | 私信对方、屏蔽或信誉处理对象 |
| score、delta | credit_score、score_delta | 信誉及其变动 |
| body | content | 帖子、消息、工单说明/回复；商品介绍仍用description |
| subject | title | 工单标题 |
| notes、missing、accessories | notes_status、missing_pages_status、accessories_status | 书籍状况，机器枚举与中文文案分离 |
| bought | purchase_date＋purchase_date_precision | 保留未知或仅知月份的含义，不伪造具体日期 |
| liked、favorited、private、muted | is_liked、is_favorited、is_private、is_muted | JSON布尔值 |
| phone_verified | is_phone_verified | 当前false |

各实体响应的状态字段统一为status，其类型分别定义为OrderStatus、TicketStatus等枚举，不能共用一个无上下文的状态词典。保留有意义的title与description区别，不为“统一”而把不同概念强行合并。

配置中用product_name、campus_name、pilot_college_name、support_hours、time_zone等明确名称。学校与院系未来用内部稳定ID关联，官方目录核实之前不凭名称猜合并或宣称认证。

## 7. 校验与公开模型

写入请求采用独立严格模型，拒绝未知字段或伪造role、credit_score、seller_id等服务器派生权限字段。必要的旧请求兼容仅在legacy适配器中处理。

公开用户模型、自身资料模型、客服视图分开；商品列表、详情、订单、工单等也使用明确输出模型。只列允许公开的字段，不返回SELECT *，不在返回后靠删除几个敏感键保密。

校验包括文本长度、金额、图片数量/角度/归属、时间范围、布尔值、分页及枚举。照片真实性、ISBN和版权判断仍不作无法证明的保证。

鉴权、订单状态、库存锁定、服务端价格核算、幂等、隐私、信誉和客服利益冲突检查继续在服务层执行，不能只依赖前端或请求字段校验。

## 8. 列表、分页、筛选和接口文档

所有列表的data采用 `{"items":[],"next_cursor":null,"has_more":false}`。默认page_size为20，最大100；不返回没有实际计算的total。

游标与所选筛选和排序绑定，使用稳定的排序键及id作为并列次序。筛选或排序改变时清空游标。消息保留增量after_id，历史读取使用before_id；均返回相同列表结构，避免目前“只取100条”丢失旧内容。

接口使用明确HTTP方法与资源路径，例如GET/POST products、GET orders/{order_id}、POST orders/{order_id}/confirm-receipt。不是为了REST命名而拆散原子交易；方法、权限、模型和幂等要求逐条进入OpenAPI。

自动生成OpenAPI和可阅读的字段字典。文档必须描述401、403、409、422、429等实际响应，校验模型不得和真正返回结构两套标准。公开文档不得包含真实账号或凭证。

## 9. 数据迁移与客户端兼容

1. 先保存包含数据库和图片的一致备份，在临时副本演练；不直接拿真实试用库做首次迁移实验。
2. 增加v1路由和模型，旧/api路径暂由适配层保留原合同；不同版本明确区分，不在同一路径随机返回新旧格式。
3. 网页、小程序和只读静态演示适配器同步迁移。两端各有唯一请求函数，负责解包、错误提示、会话变更保护和request_id，不让每个页面猜格式。
4. 客户端业务对象字段也采用snake_case；展示文字与格式放在视图层，不把另一套持久化字段重新存回服务端。
5. 更新静态演示导出、示例、CLI、健康检查、Windows启动器和部署配置；继续区分demo与trial数据目录。
6. 在旧试用数据库副本上验证账号登录、商品/图片、订单、账务与备份后再推广。
7. 所有实际使用客户端升级并完成验证后才移除legacy路径，不能只因本地网页升级就中断旧小程序。

账号密码摘要、恢复码摘要和有效订单不因规范迁移变化。旧数据缺失的书籍信息保持未知，不用默认“无缺页”填补。内部迁移日志不得保存明文密码或私人图片。

## 10. 代码风格和持续检查

Python遵循PEP8，4空格缩进，120字符行宽，使用Ruff format和Ruff check；导入分组排序，禁止一行塞多个业务语句。公共函数补类型签名，关键交易规则补说明；变量使用user_id、order_id等明确名称，避免u/p/r/d表示跨多步骤业务。

保留SQL参数化、上下文关闭连接和清晰事务边界。使用标准logging，包含操作类型和request_id；不记录完整请求体、密码、令牌、恢复码或私人证据。

网页和小程序使用同一份Prettier配置，例如2空格、单引号、分号和120字符行宽。新增依赖分为运行和开发用途，固定可复现版本，不引入付费服务。

格式化与功能修改分开提交便于审查。检查范围覆盖实际Python业务、脚本和测试，以及网页、小程序自有JS；不格式化生成资源、第三方源码和运行数据。

CI应执行格式检查、静态检查、Python测试、客户端单元验证及接口契约验证。不能通过删测试、忽略整个模块或只跑语法检查宣称完成。

## 11. 验收标准

1. v1全部JSON成功/错误响应拥有同样顶层字段，HTTP状态正确，空结果和分页一致。
2. 畸形JSON、缺字段、错误类型、未知字段、权限不足、路由/方法错误、冲突、超限和服务器异常均有契约测试；敏感输入不被回显。
3. 同一资源在列表、详情、订单快照和两端的字段、单位、时间格式和枚举含义一致。
4. 旧54项测试对应的实际业务行为持续受到验证；新测试覆盖新合同，不为了保持数量而保留无意义断言。
5. 网页和小程序适配测试继续覆盖注册、账号切换、发布、消息、订单与售后；静态只读演示也能打开。
6. 数据迁移副本中原账号可登录、原图片可访问，金额与账务不改变，旧备份能恢复；legacy兼容可验证。
7. 实际浏览器执行两账号交易与客服流程，并检查手机/电脑布局。Windows、小程序开发者工具和真机结果分别列出，未执行的不称通过。
8. format/lint均通过，OpenAPI与响应符合，README明确Python3.12及启动方法；对外仍明确模拟、未验证手机号与未接微信支付。
