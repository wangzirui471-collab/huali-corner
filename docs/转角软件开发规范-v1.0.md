**版本：V1.0 审阅草案｜日期：2026-10-17（Asia/Shanghai）**

**适用项目：转角校园二手交易与校园互助软件。**

编写依据：用户提供的《02 - CIP产品开发规范.md》V3.7、现有 `AGENTS.md`、软件功能基线 `b2fd4d2`、需求文档 V1.4 及最新工作台说明。本稿借鉴原文的章节结构和工程管理思路，改写 Java 企业平台专属约定，不复制其内部模板、链接和示例代码。

**文档性质：本稿用于审阅和约定后续开发，不代表所有条款已在当前代码中落实，不授权自动迁移框架、接口或数据库。** 已确认的用户要求与现有项目约束继续有效；如果不同文档冲突，先核对最新确认记录，不以旧文档覆盖新要求。

## 第一章 引言与适用范围

### 1.1 编写目的

让接手的人能找到代码、理解业务、复现环境、验证改动、保留原数据。优先保证交易正确、权限可靠、数据可恢复，再改善可读性、交互和性能。

本规范适用于 Python 后端、手机／电脑网页、原生微信小程序、数据库、测试、部署脚本和 AI 辅助开发。产品业务细则以最新确认的需求和验收记录为依据，不在技术规范里重新承诺赔付、收费或支付能力。

### 1.2 规则等级与现状标记

| 标记 | 含义 | 执行方式 |
| --- | --- | --- |
| 必须／禁止 | 影响正确性、权限、隐私、兼容或交付的硬约束 | 不满足时不得宣称该变更已完成；已有历史问题登记整改，不掩盖。 |
| 应／建议 | 为可维护性、效率和体验推荐的做法 | 有明确理由可采用替代方案，记录依据。 |
| 当前保持 | 已确认并沿用的架构或业务约束 | 本轮继续保留，不能借规范整理擅自改变。 |
| 新改代码适用 | 风格和工程要求的目标 | 优先用于新文件及实际修改的代码，不为达标机械重写全仓。 |
| 待迁移 | 需要兼容方案、实现与验收后才能生效 | 只描述目标，不伪称已落地，不直接破坏旧客户端。 |

### 1.3 当前技术与运营边界

| 项目 | 当前状态 |
| --- | --- |
| 后端 | Python 3.12 为推荐基线；标准库 HTTP 服务＋分层领域模块，尚未迁移 FastAPI。 |
| 数据库 | 单实例 SQLite，保留 DELETE 日志模式、现有事务组织和整数分金额合同。 |
| 网页 | 原生 JavaScript ES 模块，无须 npm 构建才能启动；共享状态集中管理。 |
| 小程序 | 原生页面与公共模块，共用后端；源码不等于微信编译、真机或审核通过。 |
| 账号 | 试用版手机号＋密码，手机号未验证，不代表实名或学籍认证。 |
| 交易 | 支付、退款、结算全部模拟；不持有真实客户资金，不开放真实服务收费。 |
| 运营 | 个人试做、计算机工程学院试点，原计划预算约 3000 元；不自动购买服务。 |
| 验证 | 云端检查、用户 Windows 实机、微信原机、公网服务须分别记录。 |

## 第二章 协作与版本管理规范

### 2.1 工作开始前

1. 阅读 `AGENTS.md`、最新交接记录和相关业务文档，核对当前分支、提交与未提交修改。
2. 先确认是新功能、缺陷、重构还是纯文档；写明这次解决什么、影响哪些数据、如何验收。
3. 拉取前检查本地修改；有协作变动时先 fetch 并比较，不盲目覆盖。不要对别人的未提交工作执行强制清理。
4. 运行测试使用独立临时目录。只有确实需要操作业务数据时才使用其受控副本，不拿真实账号库当随手测试库。

不要求每次 fetch／push 都停止正在运行的服务；替换运行文件、迁移数据库或发布时，按实际部署方案处理，避免无意义停机。

### 2.2 分支规范

| 分支 | 用途 | 规则 |
| --- | --- | --- |
| `main` | 集成后的稳定代码 | 不强推，不因功能分支通过测试就认定已经发布。 |
| `feat/<topic>` | 功能开发 | 如 `feat/staff-workspace`，从确认的集成基线建立。 |
| `fix/<topic>` | 缺陷修复 | 如 `fix/startup-loading`，记录复现、根因、修复和回归。 |
| `docs/<topic>` | 独立文档修改 | 小型文档也可跟随当前功能分支，不强制制造额外分支。 |

当前整合分支为 `feat/layered-completion`。不要为迎合模板将 `main` 改名为 master，或强制采用多客户定制分支体系。

公开／共享分支不改写历史。合并前比较目标分支并解决冲突，可采用普通 merge；squash 是否使用由仓库约定决定。私有未共享分支的整理不等于允许强推共享分支。

### 2.3 提交与审查

采用 `type(scope): 描述`，例如：

```text
feat(catalog): 增加客服商品下架入口
fix(auth): 保留网络失败时的有效会话
docs(handoff): 更新现场恢复记录
test(trade): 补充不同请求键的并发下单场景
```

类型为 `feat`、`fix`、`refactor`、`docs`、`test`、`style`、`build`、`ci`、`chore`。`ci` 用于自动化配置，不能泛指“补充提交”；`docs` 包括文档和注释，不限于注释。

一个提交应有可解释的主题，相关业务、客户端、测试和文档可一起提交；无关需求不要混入。单人开发也要在合并前做自检，可由朋友或另一位开发者复核高风险变更，不强制虚构不存在的测试部门。

审查说明包含问题与结果、关键规则、兼容／数据影响、实际验证和剩余限制。不能只写“优化代码”“测试通过”。

### 2.4 需求变更

用户已明确的常规实现细节可按确认范围推进；涉及真实收费、对外发布、数据删除、破坏性迁移或未确认的业务规则时，应先准备具体方案和可审阅结果，再确认相应变更。不能把每个小修复都变成审批流程。

## 第三章 项目结构、命名与接口规范

### 3.1 保留当前目录，不再平铺业务

```text
Backend mission/
├── server.py                  HTTP 解析与路由分发
├── manage_trial.py            本机账号管理命令
└── app/
    ├── market.py              领域服务组合根
    ├── core/                 路径、连接、事务、错误
    ├── account/              账号与资料
    ├── catalog/              商品、草稿、编辑、下架、搜索
    ├── trade/                订单、交付、模拟账务
    ├── community/            社区、聊天、校园互助
    ├── support/              工单、证据、信誉、工作台
    ├── notifications/        通知
    └── ops/                  对账、备份
web 7M/
├── index.html assets/ *.css
├── src/
│   ├── main.js router.js
│   ├── core/                 状态、HTTP、导航等基础设施
│   ├── components/           复用 HTML 片段
│   ├── pages/                页面渲染
│   ├── actions/              交互与提交动作
│   └── auth/                 账号交互
└── miniprogram/              原生小程序页面、特性、公共工具
tests/ scripts/ docs/
```

- `server.py` 不承载复杂业务；新增能力进入对应领域。必要时抽出领域内部的校验、数据访问或适配模块，不强制每个功能建立 Java 式 Controller／Dao／Mapper 全套空目录。
- 保留 `Market` 当前组合方式；是否改依赖注入或组合服务，需有独立动机和迁移方案，不顺带大改。
- 网页页面渲染、事件动作、公共片段分别归位，不把新功能全部塞进一个页面或 actions 文件。
- 共享可变状态只放 `src/core/state.js`。局部函数闭包可有临时变量，不等于允许新增跨模块状态副本或大量 `window.xxx`。
- 页面需要重绘时走 `core/nav.js` 的注册钩子，不反向 import router 制造循环。
- 路径只从后端 `app/core/config.py` 引用；保留现有带空格目录名，命令必须正确加引号，改名须覆盖部署、脚本和客户端引用。

### 3.2 统一命名词典

| 场景 | 规则 | 示例 |
| --- | --- | --- |
| Python 文件／函数／变量 | `snake_case` | `moderate_product`、`ticket_id` |
| Python 类 | `PascalCase` | `CatalogModeration` |
| 常量 | `UPPER_SNAKE_CASE` | `MAX_UPLOAD_BYTES` |
| 网页文件／CSS 类 | 多词用中横线，领域清晰 | `case-context.js`、`staff-navigation` |
| JavaScript 本地变量／函数 | `camelCase` | `ticketId`、`loadOrders` |
| JSON 与数据库新增字段 | `snake_case` | `seller_id`、`created_at` |
| 布尔值 | `is_`／`has_`／`can_`；JS 本地用驼峰 | `is_active`、`can_edit`、`hasUnread` |

业务术语统一为 `user`、`product`、`order`、`ticket`、`draft`、`post`、`room`、`notification`、`credit`、`ledger`。不为同一实体同时新增 goods／item／product 等近义名称；`order.items` 表示订单内明细，是既有集合语义。

角色、状态和类目使用固定机器值，中文只负责展示。先复用既有 `user/support/admin`、`books/living/sports/electronics` 和订单／工单状态；不能一端改值、另一端继续依赖旧值。

数据库已有 `price`、`total`、`created` 等字段不在本次直接重命名。制定词典后通过版本化 DTO／适配层渐进统一，不随意改变原字段单位和含义。

### 3.3 API 当前合同与迁移原则

**当前保持：** 现有 `/api/` 路由及其返回兼容合同继续有效，例如 `/api/products` 是数组，`/api/products/search` 是分页对象，错误常用 `error` 字段。尚未全站统一封套，也没有自动生成完整 OpenAPI。

**待迁移目标：** 新版本可采用 `/api/v1/`，资源名小写、路径多词用中横线，JSON 字段统一下划线。GET 用于只读查询，POST 用于创建及业务动作；需要时采用 PATCH／PUT／DELETE，不机械禁止这些方法。修改状态不得通过 GET。资源下架优先是可审计动作，不等于数据库物理删除。

迁移示例：`POST /api/v1/products/{product_id}/moderation`；这只是目标命名示例，不是现有可调用接口。现有对应入口为 `POST /api/product/moderation`。

迁移步骤：登记旧合同与消费者 → 定义新 schema → 增加兼容适配 → 网页、小程序、脚本同步升级 → 验证旧数据／旧客户端 → 公布切换和停用安排。不能直接给所有旧返回外包一层 data 就上线。

### 3.4 统一返回格式目标（待迁移）

所有新版本业务 JSON 响应约定同一封套；图片、下载流和明确登记的第三方回调按对应协议，不强行包 JSON。

```json
{
  "code": "OK",
  "message": "成功",
  "data": {
    "product_id": 123,
    "status": "removed"
  },
  "error": null,
  "request_id": "opaque-request-id",
  "meta": {
    "schema_version": "v1",
    "simulation": true
  }
}
```

```json
{
  "code": "VERSION_CONFLICT",
  "message": "商品已更新，请刷新后重试",
  "data": null,
  "error": {
    "fields": [
      {"field": "version", "message": "请读取当前版本后提交"}
    ]
  },
  "request_id": "opaque-request-id",
  "meta": {
    "schema_version": "v1",
    "simulation": true
  }
}
```

第二个示例对应 HTTP 409。JSON `code` 为稳定机器值，`message` 面向用户，`request_id` 关联服务端日志；不要把全部业务失败伪装成 HTTP 200。

| HTTP 状态 | 语义 | 例子 |
| --- | --- | --- |
| 200／201 | 查询／动作成功，或资源创建成功 | 下架成功、新建草稿。 |
| 400 | 参数或格式不合法 | 原因缺失、金额单位不合法。 |
| 401 | 无有效登录会话 | 令牌过期；网络失败不能冒充此状态。 |
| 403 | 已登录但无权 | 普通用户调用管理下架。 |
| 404 | 资源不存在或按权限策略不披露 | 不可见的私密资源。 |
| 409 | 状态或版本冲突 | 已被预订、草稿版本过时。 |
| 429 | 频率受限 | 提供适当的重试说明。 |
| 500 | 未预期服务异常 | 用户只见通用提示和请求编号，不返回堆栈或私密路径。 |

### 3.5 字段类型、金额、时间与分页

- 新版本金额字段建议使用 `price_cents`、`delivery_fee_cents`、`total_cents` 等显式单位，整数分；原 `price/total` 保留原合同，经适配转换，不直接替换数据库字段。
- 元输入为十进制字符串，经后端严格解析；拒绝负数、超范围、超过两位小数等不合法值。不能使用 `float * 100` 后截断替代校验。
- 新版本业务时间采用带 Z 的 UTC ISO 8601 字符串，字段为 `created_at` 等；用户界面按 `Asia/Shanghai` 展示。旧接口秒级时间戳兼容保留，不能混用秒和毫秒。
- 用户／商品／订单／工单既有数字 ID 保持类型，草稿／上传等不透明字符串 ID 不改为数字。不要强制全库改 32 位字符串主键。
- 新 JSON 布尔字段使用 true／false。缺失、null、空字符串的含义须在合同中说明，更新请求不传字段默认保留原值，是否允许 null 清空须显式约定。
- 未声明字段不得成为越权入口。旧注册接口可继续忽略权限字段以兼容，但不能采信 role／score；新版本明确采用字段白名单和无效字段处理策略。
- 列表统一为 `data.items`＋`data.page_info`。商品流／消息可用 cursor，管理列表可用 page；`page_info.mode` 区分 cursor 与 offset，不要求所有业务硬用一种分页算法。
- 游标不透明、绑定筛选和排序；稳定排序有唯一键兜底。分页上限受控，必要的目录小列表可明确登记例外。

## 第四章 编码、数据与业务正确性规范

### 4.1 Python 规范（新改代码适用）

使用 4 空格缩进、UTF-8、清晰的函数／类和导入分组。新逻辑不压成巨型单行；多条业务语句不以分号堆叠。目标行宽建议 100—120 字符，长 SQL、模板和不可断开的标识可合理例外。

关键入参与返回应有类型标注或明确的 DTO／TypedDict／数据类定义，不用没有字段说明的任意 dict 传遍各层。现阶段可逐步引入标准库类型，不为加类型强制迁移框架。

函数优先单一职责；约 50 行后检查是否需要拆分，超过约 100 行或长期承担多类职责时应说明原因并评估拆分。按展开后的可读复杂度判断，不以压缩行数“达标”。不要为凑层数拆成没有意义的空壳类。

注释说明业务依据、风险、单位和为什么这样做；关键服务写 docstring。简单自解释函数不强制作者、日期和逐行注释，修改历史用 Git。禁止吞异常后假装成功，非关键降级必须有明确边界与说明。

### 4.2 JavaScript、HTML 与 CSS

- 使用 const／let、严格比较、async／await，普通字符串单引号，模板插值用模板字符串，语句有分号；内部变量用小驼峰。
- 网络与提交错误在合适边界处理；不强制每个 async 都重复 try/catch。捕获后必须处理、转译、重抛或说明可接受的降级，不能无声丢失关键失败。
- 独立读取可并行；有依赖的请求、写操作和事务动作按正确顺序执行。提交防重复，重要请求应有超时和明确重试语义，不能自动重试不幂等扣款类动作。
- 异步操作记录原会话／账号和页面代次；晚返回结果不能覆盖新账号、较新草稿或新页面。退出和换号只清理对应账号的设备副本，不删服务端草稿。
- 动态文本进入 HTML 必须转义，URL、资源 ID 和允许的协议须校验。不得将用户输入拼为脚本、使用 eval 或允许不受控 HTML。
- HTML 使用语义化标签和可访问的表单标签；图标按钮有可读名称，图片有 alt，弹窗可键盘操作并处理焦点。
- 样式放 CSS，事件放动作模块，不使用内联事件脚本。经验证的动态样式变量／图片位置可保留，不因“一律禁止内联”破坏现有组件。
- 复用已有设计变量与组件；新增样式有业务作用域，避免无关全局覆盖。品牌配色变更需同步资源与用户确认，不顺带改色。

### 4.3 数据库与 SQL

表／字段使用小写下划线、明确关系与单位，避免保留字；不照搬 Oracle 的 `varchar2`、30 字符限制和每表全套状态／删除字段。

**必须保留必要的 NOT NULL、UNIQUE、CHECK 与已声明的关系约束。** 业务校验帮助解释错误，数据库约束负责最终兜底。历史表尚无完整外键不等于已具备外键保护；新增约束要先检查旧数据，不能直接强加导致原库无法启动。

SQL 参数必须绑定，动态表名、排序字段等无法绑定的标识必须由可信白名单选择。多表字段清楚限定归属，别名表达含义；接口 DTO 不直接透出 `SELECT *` 的全部列，内部单行读取可按需要使用后显式筛选。

用户规模增长时，应将筛选、排序、聚合与分页下推数据库，避免全量读进 Python 后再分页或每行重复查询。现有工作台仍有全量摘要聚合等可优化点，不能仅因响应分页就声称数据库分页已全部完成。

索引和 JOIN 选择依据实际查询计划及数据量；不把 COUNT(1) 一概宣称优于 COUNT(*)，不机械规定“小表必须写在左边”，不一律禁止数据库函数。包含搜索可能需要扫描，应记录规模与优化依据。

### 4.4 事务、并发与幂等

库存预留、订单生成、必要流水／审计／站内通知应按一致性边界提交；失败回滚，禁止事务中等待上传、人工输入或远端网络。

单件实物、防重复下单和重复回调必须同时考虑：事务内状态复核、原子更新、必要唯一约束、幂等键和冲突反馈。当前进程内 RLock 不能替代数据库事务、跨进程约束或生产并发验证。

编辑、下架与下单竞争时，只接受当下有效状态和版本。草稿发布重复请求应返回同一结果；相同幂等键返回同一订单不叫超卖。测试真正竞争要使用不同用户或不同请求键。

外部通知、支付等未来副作用应与本地提交分离，采用可追踪、可补偿的执行记录；不能在未来引入真实支付后继续假设“本地事务成功＝第三方已打款”。

### 4.5 迁移与原数据保护

只做有记录、可重复、先在副本验证的增量迁移；涉及原数据前确认实际 `--data`／环境变量路径并备份。禁止清库、删 var-trial、用演示账号库覆盖试用账号库来“修复”。

保持旧订单快照、实物链、图片引用、工单来源与账务记录可读。字段改名／类型改动必须提供映射、旧值处理和客户端兼容测试。框架迁移、目录改名、金额单位改变分别评估，不混在外观调整里。

### 4.6 日志、审计与隐私

服务日志记录环境、错误类别、请求编号和必要的去敏上下文，推荐标准 logging 分级输出；命令行启动提示可保留，不机械禁止一切 print。

权限变更、管理下架、退款建议／批准、信誉处罚／冲回、客服交接等有业务审计，记录操作人、对象、理由、时间及关联实体。关键审计与对应状态同事务提交。

不记录明文密码、恢复码、Authorization、支付密钥、完整私密证据、学生名单。用户可见错误不返回堆栈。限制日志和备份访问，保留／清理策略需按资料、交易争议、证据和备份分别制定，不能无限保留所有个人数据。

### 4.7 转角必须保持的业务规则

| 业务 | 不得破坏的要求 |
| --- | --- |
| 发布与书籍 | 逐本定价；实拍三图；笔记、缺页、附件明确；允许未知但不能默认承诺“无问题”。4 元为提示，允许 0 元。 |
| 草稿 | 私密、按账号隔离、版本冲突提示；关闭后可继续；到期策略明确。 |
| 商品管理下架 | 管理员／客服可操作在售商品，原因必填、审计与通知；卖家不能自行恢复 staff_delist，不自动扣分。 |
| 合并取货 | 同卖家合并，商品与送货费分开；现有送货费取最高一次，不静默更改计算方式。 |
| 订单与价格 | 成交快照固定，不支持订单外补款；改约需按规则确认，商品修改不回写历史订单。 |
| 自动收货 | 与下单后确认安排不同；当前从买家核对交接计 24 小时，争议暂停，不以卖家单方送达开始自动放款。 |
| 退款与重售 | 仅退款不恢复库存；退货实物确认、退款完成及争议关闭后才按现有流程生成重售草稿。 |
| 信誉 | 100 分起，低于 60 限制新发布；经核实、关联工单、按规则、可申诉；点赞／举报／退款不直接扣分。 |
| 校园互助 | 首版发布＋私聊＋举报反馈，不把聊天价格当作已支付服务订单。 |
| 模拟资金 | 全程明示模拟，不展示真实收款码冒充担保，不承诺平台包赔或真实支付成功。 |

## 第五章 页面与菜单规范

### 5.1 信息结构

买卖流程优先“看清商品 → 确认费用与约定 → 下单 → 交付 → 售后”。发布优先选项、合理默认和可选补充，不把所有高级字段首屏平铺；默认值不能替卖家作真实性承诺。

管理员与客服使用独立工作台，电脑和手机均有可见入口；概览展示需要处理的事，不以商品购物导航替代管理导航。

菜单优先高频待办、业务顺序和角色职责，通常不超过两至三层。设置／系统管理不机械排在最前，也不要求每个菜单强行使用不同颜色与图标。

### 5.2 表单、列表与操作

- 必填、可选、未知、暂不支持明确；字段旁说明版本、单位和限制，不把校验失败变成泛化“保存失败”。
- 列表展示关键标识、状态、负责人和更新时间；金额便于比较，长文可展开，常用筛选易找，更多条件折叠。
- 区分加载中、真正无数据、无搜索结果、无权限、加载失败，提供重试；页面不能无限停留在“正在打开”。
- 无权限按钮隐藏，状态不允许的操作可禁用并说明原因；服务端仍独立校验。
- 下架等破坏公开状态的操作用危险色并确认；退款／扣分展示对象、金额／分数变化、依据和后果。批量操作明确数量和成功／失败结果。
- 支持 375、390、768、1440 等代表宽度检查，避免整页横向溢出；弹窗按视口布局，不固定照搬桌面像素尺寸。
- 状态兼有文字和色彩，不能只靠红绿辨认；按钮名称描述动作，不在举报工单上显示含糊的退款按钮。

### 5.3 启动、登录与提醒

启动失败应区分资源加载、接口、会话和存储问题；网络故障不能无依据清除有效账号。修复要验证完整启动和登录，不只把加载文案换成报错就宣布根因解决。

浏览器／微信通知分别声明送达条件；权限申请不等于实现离线推送。启用客服账号不等于客服在线，服务时段不等于实时响应承诺。

## 第六章 权限与账号规范

### 6.1 角色边界

| 能力 | 普通用户 | 客服 | 平台管理员 |
| --- | --- | --- | --- |
| 自己的商品、草稿与订单 | 归属／状态允许时可操作 | 作为普通交易方同样校验 | 作为普通交易方同样校验 |
| 管理下架在售商品 | 不可 | 可，需原因 | 可，需原因 |
| 非本人相关工单详情 | 不可 | 认领／受指派且无利益冲突时可 | 无利益冲突且职责允许时可 |
| 退款建议／内部备注 | 不可 | 在受权工单可 | 可 |
| 退款批准、信誉处罚／冲回 | 不可 | 不可 | 满足流程与依据时可 |
| 客服授权、账务、审计、备份 | 不可 | 不可 | 可 |

群主／群管理员权限仅限对应群，不自动拥有客服、账务或平台权限。工作人员不能审批本人或存在利益冲突的案件。

### 6.2 每个接口的校验

操作者 ID 来自有效登录会话，不能由请求体伪造；目标用户／商品 ID 可以作为参数，但必须校验操作者对该对象的权限。不能把“禁止前端传用户 ID”误解为接口不能传目标 ID。

读取区分公开 DTO、当事人详情、工作人员受权详情；未认领客服只看摘要，私密证据和内部备注不因队列可见而泄露。修改时再次检查角色、账号启用、对象归属、版本、状态与必要的交易资格。

### 6.3 密码与运营者操作

独立管理员／客服账号，不共用密码；普通注册不提升权限。密码、恢复码和会话按现有安全方式管理，修改／重置后撤销旧会话。

本机 `manage_trial.py` 只能由有服务器操作权的人使用，并指向与网站相同的数据目录；网页客服权限不等于服务器重置权。不能仅凭未验证手机号恢复账号。

人员停用要撤销会话、处理未结工单交接并留痕；不得把所有未结事项静默丢给失效账号。

## 第七章 开发、测试与完成标准

### 7.1 开发流程

确认场景与验收 → 检查现状／复现缺陷 → 实现最小必要变更 → 自动检查与业务回归 → 审查数据和兼容影响 → 更新文档 → 按约定交付。

交易、权限、并发、隐私和账务等高影响变更先补能反映错误的测试，再修复；简单可逆的布局／文案用合适的浏览器检查，不编写镜像实现的无效测试。

### 7.2 必测场景

| 类别 | 代表验证 |
| --- | --- |
| 启动与登录 | 完整包首屏、缺文件／失败提示、错误密码、过期会话、网络失败、正确账号恢复。 |
| 权限 | 普通／客服／管理员正反向；归属、未认领证据、内部备注、利益冲突、停用后会话。 |
| 商品与草稿 | 三图、金额／缺陷、重复发布、版本冲突、换号晚返回、编辑与下单竞争。 |
| 订单与资金 | 不同键并发、重复请求、合并费用、取消／交付／争议／退款／结算的边界与回滚。 |
| 售后与信誉 | 实物退回条件、仅退款不重售、处罚防重、申诉冲回、确认取消无副作用。 |
| 数据与交付 | 旧库增量迁移、备份句柄关闭、恢复、源码包无数据、静态演示只读与子路径。 |
| 多端 | 网页响应式、JS 模块与 MIME；小程序逻辑、工具编译、真机结果分别记录。 |

### 7.3 现有验证命令

从项目根目录运行，按环境使用 python 或 python3：

```bash
python -m unittest discover -s tests -v
node tests/frontend_modules.test.mjs
python tests/staff_workspace_browser_smoke.py
python tests/layered_browser_smoke.py
python tests/functional_help_browser_smoke.py
python tests/windows_assets_smoke.py

```

还应按改动运行 `tests/frontend_*.mjs`、`tests/native_*.test.js` 及相关浏览器脚本。浏览器路径要适配目标环境；修改脚本定位器可以跟随真实 UI 变化，但不能删断言来掩盖失败。

### 7.4 完成定义

必须给出实际执行的命令、环境、结果和未运行项；先看结果再声称通过。零测试、语法通过、模块加载通过和完整业务通过不是一回事。

新功能有对应验收，关键数据／角色负向场景通过，相关回归通过，文档与版本一致，交付文件完整；保留缺口与设备限制。测试失败须说明原因和影响，不能仅报通过部分。

### 7.5 缺陷与现场反馈

缺陷记录包含网址／端口、版本与分支、启动／数据目录、复现步骤、第一条错误、预期、实际、影响和去敏材料。优先级按数据／安全／主链路损害确定，不凭截图猜根因。

个人试做不写无人能兑现的固定 SLA。紧急问题先止损、保留现场与原数据，再定位修复；由用户或实际环境验收后关闭。用户说“已恢复”可记录恢复，但没有证据时不写“已找到根因／代码已修复”。

## 第八章 环境、部署、备份与回滚

### 8.1 环境复现

记录 Python、依赖、浏览器／Node、SQLite 和启动参数；依赖在清单中固定，工具环境与产品依赖分开。格式化、lint、类型检查和 CI 推荐逐步引入并固定配置，**当前未交付完整自动化配置，不能声称这些检查已全部启用**。

源码、演示数据、试用数据、测试临时数据分别存放。`var/` 与 `var-trial/` 不混用；源码包排除数据库、uploads、backups、令牌、真实环境文件和原始学生表。

### 8.2 更新前与更新后

确认目标环境和版本 → 识别实际数据目录 → 保存旧代码及一致性数据备份 → 在副本验证迁移 → 选择有人值守的低峰窗口 → 整套更新 → 启动检查 → 首页／登录／商品／订单／工单验证 → 记录结果。

不要求一律晚上 20 点后部署；时间由校园使用情况和运营人员实际可用时间确定。只换 server.py、漏 ES 模块或仍连旧端口都不算完整更新。

### 8.3 备份与恢复

数据库与上传图片需对应，记录备份时间、文件、大小和失败状态。另存受控副本、检查磁盘并定期演练恢复；创建成功不等于恢复可用，也不等于备份已异地保存。

恢复到新空目录，停止旧服务，显式指定数据目录，核对账号、照片、订单、工单和对账。备份含私人数据，不开放公共下载或提交源码仓库。

### 8.4 回滚与外部发布

先判断代码能否兼容现有 schema；更新后已有新交易时，不直接恢复旧数据库丢弃增量。暂停写入、备份最新现场，评估代码回滚、前向修复或受控的数据恢复，记录新增数据如何保留和对账。

公网模拟试用需要实际 HTTPS 服务、受控代理、持久数据目录、监控和目标网络验证；本机 127.0.0.1 只能本机访问。静态演示不能冒充带注册和交易的服务。

真实支付、短信、微信审核、服务收费属于独立准入与实现阶段，需要核实主体、服务方和费用。不能因为普通商户能收款就宣称具备平台担保／延迟结算能力；不能自动购买付费资源。

## 第九章 需求调研与产品变更规范

每项需求至少记录用户、场景、问题、目标、范围外、数据／权限、异常情况与验收例子。把“有这个按钮”和“流程能闭环”分开核对。

优先观察真实学生发布、找书、约取、申诉和客服操作；先小范围试点，不为铺满学院目录制造虚假活跃。录音／访谈材料征得参与者同意并去敏，不把真实聊天和学生表直接交给外部 AI。

原话、推断和已确认规则区分标记，变更保存原因、日期、确认人和影响。学校／学院名称的来源与核实状态明确，自填资料不生成认证徽章。

产品功能、技术重构、运营政策分开说明；不能借新增校园互助顺带启用真实代收服务费，也不能借统一规范改掉用户已经确认的合并费率或收货计时起点。

## 第十章 开发文档与 AI 协作规范

### 10.1 文档分工

| 文件 | 应说明什么 |
| --- | --- |
| README | 怎样获取正确分支、完整启动、更新与验证，当前限制。 |
| 需求文档 | 产品行为、状态和未完成项，不把目标当已实现。 |
| 开发规范 | 工程规则、命名、接口目标及兼容约束。 |
| AGENTS.md | 已确认、适用于执行开发的项目约束；本草案不自动覆盖它。 |
| 接口／字段词典 | 真实接口、字段、单位、类型、权限、状态及版本变化。 |
| 交付／交接记录 | 软件提交、验证、数据目录、待办、故障事实和限制。 |
| 关键决策记录 | 为什么保持或改变数据库模式、框架、接口与其他长期取舍。 |

文档随实际行为变化更新。Markdown 可作为受版本管理的主稿，Word 便于 WPS 编辑；应避免两份各自修改后长期不同步。没有真实创建在线协作链接时，不声称已建立在线 WPS 文档。

### 10.2 AI 辅助开发

1. 给 AI 明确目标、当前基线、数据边界和验收例子；要求先读相关模块与约束，不猜测文件和 API。
2. 生成代码按现有分层落位，复用已验证的路径、金额、权限与事务入口，不另建一套隐含规则。
3. 不向 AI 或第三方服务提交真实密码、令牌、完整数据库、工单私密证据和原始学生表；使用合成、最小化或经授权去敏材料。
4. 外部开源代码先核对维护情况、许可证、依赖和用途；不复制不明代码，也不为引入某仓库强行重写现有项目。
5. AI 输出要看差异、测行为、核对权限与数据；禁止用“模型说修好了”替代实际验证。
6. AI 可自动完成确认范围内的可逆开发和检查，但不能自动删除数据、付费、启用真实资金或冒充已上线／原机验证。
7. 明确报告已完成、未完成和假设；当用户改变优先级时保留原待办，停止无依据修改，不把用户自行恢复归功于代码修复。

## 第十一章 原模板调整意见与落地顺序

### 11.1 是否需要修改原模板

**需要。保留工程原则，改掉不适用于转角或不正确的绝对规则。**

| 原模板条目 | 转角处理 | 理由 |
| --- | --- | --- |
| Git、分层、审查、测试、回滚、需求记录 | 保留并简化 | 个人与小团队也需要，但不照搬完整企业审批链。 |
| Java／Spring／Mapper／Oracle 专属命名和目录 | 改写 | 当前是 Python、SQLite、ES 模块，不需要复制框架外壳。 |
| “禁止非空、唯一约束，改由代码实现”（4.1） | 不采用 | 会削弱交易、幂等与账号一致性的数据库兜底。 |
| 全库 32 位字符串 ID、标识符不超 30 字符、text 必须分表 | 不直接采用 | 不是 SQLite 通用限制，迁移成本与业务收益不匹配。 |
| GET 只显示页面、禁止 PUT／DELETE、末段强制驼峰 | 改写 | 以 HTTP 语义、可读资源和现有合同兼容为准。 |

### 11.2 软件是否需要按规范整改

**需要逐步整改，但不建议为了套规范重写已可用的交易系统。** 当前文件和方法仍有压缩长行，返回格式、字段和分页策略也未全部统一；应诚实登记，按风险和收益推进。
